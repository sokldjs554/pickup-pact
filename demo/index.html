고객은 주문을 취소했는데,
왜 점주 정산과 포인트가 남았을까?

이 데모는 예약 픽업 주문에서 메시지가 늦거나 중복으로 도착해 주문·결제·정산·적립 상태가 서로 어긋났을 때, 백엔드가 실제 발생 순서를 복원하고 잘못된 금전 처리를 안전하게 되돌리는 과정을 보여줍니다.

대표 상황: 12:30 픽업 주문 고객 취소: 12:14:10 취소 메시지 도착: 12:15:02 그 사이 정산 9,000원 + 90P 적립

3 · Pickup Pact의 처리
“도착한 순서”가 아니라 “실제로 발생한 순서”로 다시 판단합니다.
1취소가 정산보다 먼저 발생했다는 사실을 복원
2이미 기록된 정산은 삭제하지 않고 반대 분개로 취소
3잘못 지급된 포인트를 회수하고 조회 상태를 다시 생성
최종: 주문 취소 · 정산 취소 · 포인트 회수

백엔드 판정 및 복구 결과
아래 버튼을 누르면 FastAPI 백엔드가 시나리오를 계산합니다.
정적 애니메이션이 아니라 실제 API 응답으로 결과를 표시합니다.
개발자용 기술 상세 보기
핵심 판정
occurred_at과 received_at을 분리해 실제 업무 발생 순서를 복원합니다. Kafka의 at-least-once 전달은 event ID와 semantic fingerprint로 중복/충돌을 구분합니다.
복구 방식
금전 이력은 삭제하지 않고 REVERSE_SETTLEMENT, REVERSE_REWARD 같은 보상 명령을 생성합니다. CQRS 조회 상태는 canonical event timeline에서 재구성합니다.
