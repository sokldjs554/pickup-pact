## 실제로 재현한 문제

### 1. 깨진 유니코드 JSON으로 HTTP 500 발생
JSON으로 표현된 단독 UTF-16 surrogate가 명령 해시 또는 검증 오류 응답의 UTF-8 인코딩을 실패시켰다. 수령 코드만의 문제가 아니어서 견적 ID, 알 수 없는 중첩 키, 주문 입력, 실험 입력도 시험했다.

`tests/route/test_final_input_audit.py`의 15개 반례가 수정 전 500을 재현했다. JSON 경계에서 해당 문자를 먼저 거절해 400을 반환하고, 기존 주문/지갑/이벤트가 바뀌지 않도록 한다. 정상적인 한글/이모지 및 빈 본문·null·배열·문법 오류는 기존 스키마 검증 계약을 유지한다. 최초 수정 중 빈 본문에서 생긴 회귀도 별도 반례로 잡아 수정했다. 새 400 응답은 OpenAPI 스냅샷에 함께 반영한다.

### 2. 거절되는 예약 변경이 새 용량을 먼저 확보
Kotlin `CommitmentService.renegotiate()`는 Redis lease 포트 호출 뒤 도메인 전이를 계산했다. 전이 계산이 예외를 내면 뒤에 연결된 DB 저장 오류 복구를 거치지 않아, 거절된 요청이 새 용량을 만료 때까지 차지할 수 있었다.

테스트 전용 commit `83ceb90f1f3ba8e2855f2928bd78f260d7e7fb61`의 실제 JVM CI에서 `RescheduleAdmissionTest` 5개가 모두 실패했다. HELD/CANCELLED/PICKED_UP, 취소 판단 중, pact 없음 상태 각각에서 acquire 호출 횟수가 0이어야 하지만 1이었다. 빌드 오류가 아니라 단언 실패임을 확인했다.

수정은 순수 도메인 전이를 먼저 검증하고, 그 결과에 나중에 확보한 lease만 넣는 방식이다. 기존 저장 실패 시 새 lease 해제, 성공 후 이전 lease 해제 경로는 유지한다. 이는 모든 네트워크 단절·프로세스 종료를 해결하는 분산 트랜잭션이 아니다.

### 3. 현재 제품과 공고 설명 불일치
`docs/jd-traceability.md`에는 주력 결과물이 복구 작업대이고 root가 예전 주문 UI라는 설명이 남아 있었다. 새 주문/쿠폰/포인트 흐름, `/classic` 경로와 각 실행 환경을 기준으로 다시 작성했다. 실제 운영하지 않은 기술은 별도 범위로 표시한다.
