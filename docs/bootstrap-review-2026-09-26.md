# 새로고침 후 지갑이 보이지 않던 초기화 순서 점검

main `9a8c9dfb686283ad208ab84d90d546d4b2b5b4f0`의 공개 검증 `36238833538`에서 모바일 취소 후 새로고침 시 `#availablePoints`가 사라졌습니다. 취소 전·후 동일 페이지의 2,000P 검사까지 통과한 뒤, 새로고침 후 검사에서 실패했습니다. 실패 당시 접근성 트리에는 취소된 주문의 기본 카드가 있지만 지갑·혜택·이관 확장 내용이 없었습니다. 이 원본 실패는 삭제하거나 성공으로 바꾸지 않습니다.

## 원인과 재현

`product.js`는 첫 번째 deferred script인데, 실행 즉시 비동기 초기화를 시작했습니다. 이미 저장된 주문을 API로 빨리 읽으면 뒤에 오는 `benefits-ui.js`·`handoff-ui.js` 등의 이벤트 구독보다 먼저 `route:render`를 보낼 수 있었습니다. 기본 주문은 그려졌지만 뒤늦게 등록한 확장 화면은 초기 이벤트를 놓칠 수 있습니다.

실패 실행은 새로고침 시의 개별 자바스크립트 응답 시간을 보존하지 않았으므로 그 실행에서 어떤 파일이 몇 밀리초 늦었는지는 단정하지 않습니다. 실제 시작 코드를 실행한 제어된 Node 시험에서는 늦은 구독자가 초기 주문을 받지 못하는 같은 순서 문제를 재현했습니다. 6개 검사 중 2개 실패 뒤 초기화 수정 후 6개가 통과했습니다.

## 수정

정적 HTML의 deferred script들이 모두 실행된 `DOMContentLoaded` 뒤에 초기 주문을 복원합니다. 중복 초기화를 막고, 이미 완전히 로드된 문서에서 실행하는 경우는 바로 초기화합니다. 단순히 `readyState !== 'loading'`을 쓰지 않습니다. deferred script 실행 중에는 아직 다른 스크립트가 남아 있어도 `interactive`이기 때문입니다.

기존 취소·혜택·금액·자동 복구 로직이나 브라우저의 금액 단언은 바꾸지 않았습니다. 공개 혜택 검사에 실패 화면·API 상태·브라우저 오류·실제 리소스 시각을 남기도록 진단만 추가했습니다.

## 별도의 실제 브라우저 회귀

`verify_bootstrap_browser.py`는 테스트 서버가 원래 `benefits-ui.js` 바이트의 전송만 1.5초 늦춥니다. API는 실제 앱/저장소/HTTP로 처리합니다. Playwright 요청 가로채기나 가짜 응답, 금융 데이터 교체는 없습니다. API로 실제 주문·취소를 만든 뒤 브라우저가 저장된 주문을 열고 새로고침할 때 2,000P·취소 복원·주문 ID가 표시되는지 검사합니다. 리소스 응답 완료 뒤 초기 API 요청이 시작됐는지도 확인합니다. 이 통제된 느린 로딩 검사는 공개 서버의 응답 속도 측정이 아닙니다.

실제 공개 혜택·주문·복구·조건·문구 검증은 새 main SHA로 다시 실행합니다. 통제된 단위검사만으로 공개 검증을 대체하지 않습니다. 이전 지갑 표시 실패와 처음의 지역 환경 pytest 시간 제한은 기록에 남깁니다.

관련 브라우저 규칙: https://developer.mozilla.org/en-US/docs/Web/API/Document/DOMContentLoaded_event
