# 변경 조건과 비교 기준 보완

기준 앱: 8dee63822020d2217a91882cedaf9badf9988f90. 이번 변경은 지원서가 아니라 프로젝트 자체의 보완이다. 사용자에게 화면·검증 결과를 먼저 제시하고 자기소개서/포트폴리오는 이후 작성한다.

## 새로 코드가 확인하는 것

새 체험은 partner-transfer-v1을 사용한다. 모퉁이/웨이브/오트는 가상 참여 그룹이며 가든/에스프레소는 미참여다. 미참여 매장에 최초 주문은 가능하지만 이관은 막는다. 용량360mL·아이스·우유·디카페인 조건을 맞춘다. 같은 메뉴명이나 용량이 같은 맛을 뜻하지는 않는다. 기준은 원래 주문에 저장한 상품 조건이며 바뀐 카탈로그로 원래 선택을 바꾸지 않는다.

quote_id에 참여 정책 버전·상품·가격·할인 부담 조건이 포함된다. 조건이 바뀌면 같은 상태 버전이어도 이전 견적을 거절한다. 확인 버튼으로 해당 견적을 수락한 사실과 조건을 ORDER_TRANSFERRED에 기록한다. 실제 점주 계약을 체결했다는 뜻은 아니다.

전 매장 쿠폰과 사용 포인트(데모에서 1P=1원)는 플랫폼 부담으로, 매장 전용 쿠폰은 해당 매장 할인으로 모델링한다. 고객 현금+플랫폼 쿠폰+플랫폼 포인트 부담=매장 모의 수취액이다. 신규 적립 포인트는 이 수취액에 다시 더하지 않는다. 수령 시 같은 트랜잭션 후보에 1회만 기록하고 거절/응답 누락 단계에서는 정산을 확정하지 않는다. 실제 PG 승인 변경·환불·세금·가맹 계약은 연결하지 않았다.

## 더 강한 기준도 비교

기존 유지/취소우선 재주문/같은 주문 이동 외에 **새 자리 확보 후 재주문**을 추가했다. 이 기준은 같은 저장된 이관 엔진과 매장 프로토콜을 사용하고, 성공하면 기존 주문을 취소하고 새 ID·재승인·혜택 재검증을 기록한다. 별도 경쟁 서비스나 독립 구현 검증이 아니다. 동일 안전 절차이면 거절/마지막 자리 경쟁에서 원래 주문 보존은 동률이다. 주문 ID 유지와 승인 횟수가 달라도 사용자 만족이나 사업 성과가 측정됐다고 말하지 않는다.

비교는 6상황×4정책. 실행당 저장소 초기화는 24회에서1회로 줄이되 각 경우의 world와 주문은 분리한다. SQLite 내구성 옵션은 낮추지 않았다. benchmark_comparison_setup.py가 이전 초기화 방식과 결과 해시를 대조하고 실행 순서를 번갈아 측정한다. 로컬 수치는 공개 서버 지연/부하 개선을 대신하지 않는다.

## 화면/API

첫 문구는 주문 보존과 자동 확인을 앞에 둔다. 변경 확인창에는 용량·옵션, 맛의 차이, 참여 조건과 금액을 함께 표시한다. 영수증에는 고객/플랫폼/매장 부담을 구분한 모의 수취액이 나온다. 서버 갱신은 아직 적용하지 않은 상황 선택을 지우지 않는다.

주문·지갑·견적·이관·비교·영수증·런타임 응답을 이름 있는 모델로 정의하고 중요한 금액 균형을 검증한다. 이벤트 data와 추가 메타데이터는 호환성을 위해 열린 객체다. 모든 응답이 완전 폐쇄형 모델이라고 주장하지 않는다.

## 구현만으로 채울 수 없는 항목과 확인 계획

고객 검증: 같은 용량/옵션이어도 원두와 맛이 다른 음료를 받을 의사가 있는지, 가격 차액과 대기 사이 선택, 복구 안내 이해도를 실제 체험 후 묻는다. 인터뷰를 수행하지 않았으며 응답을 만들어 넣지 않는다.

점주 검증: 제조 전 이관 참여 의사, 미제조 취소 수수료 필요 여부, 대체 주문 유입/이탈의 균형, 할인 비용 합의, 마감 시각 운영 제약을 확인해야 한다. 현재 비용 정책은 연구용 가정이다.

운영 검증: 실제 PG의 승인/재승인 규칙, 가맹점 인증, 다중 호스트/DB 유실, 실제 운영 SLA와 팀 협업 경험은 이 구현으로 대체할 수 없다. 이를 위해 새 서비스 흉내나 임의 수치를 추가하지 않는다.

## 완료 판정

구현/검증 명령은 해당 작업의 결과 로그와 최신 커밋으로 확인한다. 이전 영상은 이전 앱의 녹화이며 새 참여 규칙과 네 정책 비교를 보여준다고 설명하지 않는다. 신규 화면의 실제 브라우저 캡처와 공개 배포 검증은 해당 SHA의 artifact에 기록한다. 통과하지 않은 항목은 완료로 표시하지 않는다.
