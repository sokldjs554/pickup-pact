# 거절돼도 주문이 남는 매장 변경

## 달라진 경험
기존에는 주문의 매장 정보를 한 번에 바꿨다. 이번 버전은 새 매장의 수락을 먼저 확인하고, 거절되면 원래 주문·쿠폰·포인트를 유지한다. 답이 끊기면 성공이라고 안내하지 않고 서버가 저장된 같은 작업을 자동으로 확인한다. 반복 확인이 끝나지 않으면 주문을 보관한 채 **‘처리 결과 다시 확인하기’**를 제공한다.

주문 카드 아래에서 다음 상황을 직접 설정한다. 거절되거나 확인이 필요한 경우 안내 카드는 주문 정보보다 앞에 나온다.

- 새 매장 거절: 변경 전 주문과 혜택을 그대로 유지한다.
- 새 자리 확보/기존 자리 반환/새 매장 인계 뒤 응답 끊김: 새로 주문하지 않고 저장한 작업을 재확인한다.
- 다른 체험 손님의 주문: 같은 회차의 한정된 제조 자리를 함께 사용한다. 마지막 자리를 먼저 잡으면 뒤의 변경은 거절한다.

쿠폰·포인트는 이전 정책을 유지한다. 전 매장 500원 쿠폰과 1,000P를 쓴 웨이브 라떼는 2,800원이다. 오트로 변경하면 같은 쿠폰과 포인트가 유지되고 메뉴 차액 400원으로 3,200원이 된다. 웨이브 전용 쿠폰을 골랐다면 새 매장에서 할인받지 못하므로, 메뉴 차액과 할인 차이를 확인한 뒤 동의해야 한다.

## ‘한 DB에서 원자 변경’과 달라진 구현

주문·지갑은 기존 `JourneyStore`가 담당한다. 매장은 `MerchantFleet`가 담당하고 **매장마다 별도의 SQLite 파일**에 자리와 처리 영수증을 저장한다. 주문 저장소의 롤백으로 매장 저장소의 커밋을 되돌릴 수 없다. 실제로 매장 커밋 직후 `os._exit(91)`로 프로세스를 종료하고 재시작하는 시험을 수행한다.

파일 위치는 `ROUTE_DB`와 그 옆의 `<ROUTE_DB>.merchants/`다. 복구를 위해서는 **주문 DB와 모든 매장 DB 및 WAL 파일을 함께 유지**해야 한다. 컨테이너 임시 디스크가 교체돼 이 파일이 없어지는 상황까지 복구한다는 뜻이 아니다.

한 체험 회차는 `world_id`로 분리된다. 공개 입력에서 다른 회차에 들어갈 수 없고, 화면의 체험 손님은 해당 회차의 매장 접수 명령만 사용한다. 자동 테스트에서는 서로 다른 두 `JourneyStore`와 독립 coordinator DB가 동일 매장 DB의 마지막 자리를 놓고 경쟁한다. 계정 간 공유 포인트는 구현하지 않았다.

**공개 앱 실행 경로는 별도 프로세스의 매장 역할 서버에 실제 HTTP 요청을 보내며 매장별 DB는 분리된다.** 실제 가맹점이나 실물 제조기를 연결한 것은 아니다. 동일 호스트에서 프로세스를 나눈 구조이며 멀티 호스트 고가용성은 아니다. 비교 실험은 동일 명령을 로컬 매장 어댑터로 실행한다. 새 코드가 기존 JVM/Kafka/PostgreSQL 서비스를 호출한다고 설명하지 않는다.

## 저장되는 처리 순서

| 단계 | 실제로 확인하는 것 | 아직 할 수 없는 일 |
|---|---|---|
| FREEZE | 기존 매장의 주문을 잠시 고정 | 기존 매장에서 제조 시작 |
| HOLD | 새 매장에 제조 자리 보류 | 새 매장에서 제조 시작 |
| DECIDE | 변경 결정을 주문 DB에 저장 | 응답 불명 상태를 실패로 단정해 되돌리기 |
| RELEASE_SOURCE | 기존 매장의 자리 반환 | 기존 세대 요청으로 제조 시작 |
| ACTIVATE | 새 매장에 제조 권한 인계 | 두 매장에서 동시 제조 |
| FINALIZE | 같은 주문의 매장·혜택·이벤트 확정 | 이미 확정한 혜택의 중복 차감 |

HOLD가 거절되면 새 매장에 취소 표식을 남긴 뒤 기존 제조 고정을 해제한다. 표식은 늦게 도착한 예전 HOLD/ACTIVATE를 막는다. 거절 후 다시 시도할 때는 세대 번호를 올려, 이전 표식 때문에 정상 재시도까지 막히지 않게 했다.

단계마다 **작업 ID + 단계**를 같은 요청 키로 재사용한다. 매장 DB는 효과와 처리 영수증을 같은 트랜잭션에 저장한다. 응답이 없어 재시도하더라도 원래 결과를 읽으며, 요청 키의 내용이 바뀌면 거절한다. 사용자 화면은 PENDING/REJECTED 결과를 성공 토스트로 바꾸지 않는다.

응답이 불명확할 때 임의로 원래 주문을 다시 활성화하면 두 매장이 만들 수 있다. 따라서 COMMIT 결정 뒤에는 그 작업을 끝내는 방향으로만 재확인한다. 임시로 제조 가능한 매장이 0곳이 될 수 있지만 2곳이 되게 하지는 않는다. 보류 중에는 두 매장의 자리를 잠시 점유할 수 있다. 가용성과 처리량보다 중복 제조 방지를 우선한 선택이다.

## 취소 후 재주문과의 비교

`POST /api/route/transfer-comparison`은 유지·취소 후 재주문·확인 후 같은 주문 변경의 세 방식을 **동일한 실제 명령 처리기**로 실행한다. 조건과 동작이 같을 때 결과가 같은 경우도 남긴다.

| 상황 | 취소 후 재주문 | 확인 후 같은 주문 변경 |
|---|---|---|
| 정상 수락 | 새 주문으로 접수 | 기존 주문 번호로 접수 |
| 견적 확인 뒤 거절 | 기존 주문은 취소됐고 새 주문은 없음 | 기존 주문·혜택 유지 |
| 견적 확인 뒤 마지막 자리 선점 | 새 주문 접수 실패 | 기존 주문·혜택 유지 |
| 수락 응답이 한 번 끊김 | 같은 재주문 요청을 재시도해 복구 | 같은 변경 요청을 재시도해 복구 |
| 기존 매장이 이미 제조 시작 | 변경하지 않고 원래 주문 유지 | 변경하지 않고 원래 주문 유지 |
| 보류 중인 전 매장 쿠폰이 만료됨 | 취소로 보류를 풀면 새 주문에는 적용 불가 | 기존 보류를 이어가는 정책에 따라 유지 |

마지막 쿠폰 사례만 `morning10`과 90분 마감으로 명시적으로 설정한다. 기존 매장이 거절하는 상황, 실제 시장 빈도, 모든 장애 조합을 대표하는 실험은 아니다.

비교 기준도 변경 전에 금액과 조건을 확인하고, 응답 불명일 때 동일 멱등키로 재시도한다. 제조 시작 상태를 알면서 취소하도록 일부러 나쁘게 만들지 않는다. 취소 후 재주문의 자원 보장 범위가 달라서 생기는 결과를 보여주는 것이지, 다른 상용 앱의 실제 구현을 실행한 것이 아니다. 재주문 쪽도 새 자리를 먼저 잡는 절차를 도입하면 차이가 줄어들 수 있다.

표의 요청 횟수는 공통 주문 이후의 서버 명령 횟수이며, 사람의 클릭·체감 지연·성능 수치를 측정한 값이 아니다. 예상 도착 시간도 기존 합성 경로 계산을 사용한다. 이전의 120건/시드 실험은 변경하지 않고 별도 결과로 유지한다.

## 실행과 재현

```bash
python -m pip install -r demo/requirements.txt
python -m uvicorn demo.main:app --host 127.0.0.1 --port 10000
```

기존 세션은 강제 이관하지 않는다. **‘새 체험’**을 눌러 새 매장 기록이 있는 주문을 만든다. 기존 `/classic`, `/repair-lab`도 유지한다.

```bash
# 저장·경합·강제종료·API 시험
PYTHONPATH=.:services/reconciler python -m pytest -q tests/route
# 6가지 상황 × 3정책을 3회 재실행; 반복을 새 표본으로 세지 않음
python scripts/run_transfer_comparison.py --repeat 3 --output verification/transfer-comparison
# 앞서 띄운 서버에 실제 HTTP 요청
python scripts/verify_handoff_http.py --repeat 3
# 실제 브라우저는 별도 확인: Playwright와 Chromium 필요
python scripts/verify_handoff_browser.py --repeat 3
node scripts/verify_handoff_labels.cjs
```

Windows PowerShell에서는 `$env:PYTHONPATH=".;services/reconciler"`를 설정한다. 요청 비교 API는 한 프로세스에서 동시 2개로 제한하며 초과하면 429와 Retry-After를 반환한다. 이 제한이 운영용 속도 제한이나 인증을 대신하지는 않는다.

## 검증 경계와 남은 일

ASGI lifespan에서 매장 HTTP 프로세스와 `RecoveryWorker`를 시작한다. 내부 통신 토큰은 실행 시 생성하고 브라우저에 보내지 않는다. 매장 프로세스가 종료되면 감독 스레드가 재시작하며 저장된 처리 영수증을 재사용한다. 호스트가 바뀌거나 DB 파일이 유실된 경우는 이 복구 범위가 아니다.

자동 복구는 1초 주기로 실행 시각이 된 작업을 최대 16개씩 읽는다. 최초 3초부터 최대 30초까지 간격을 늘리며, 답을 확인하지 못한 횟수가 8회가 되면 추가 확인 상태로 남긴다. 고객 주문·혜택이나 제조 권한을 임의로 풀지 않는다. 사용자가 재확인하면 저장된 같은 작업을 이어간다.

변경 결정(COMMIT)을 저장하기 전 45초 이상 지연된 작업은 ABORT 결정을 기록하고, 새 매장 보류를 해제한 다음 원래 매장 주문을 재개한다. 해제나 재개 응답도 모호하면 확인 상태를 유지한다. 이미 COMMIT한 작업은 시간이 오래됐다는 이유만으로 원래 매장에서 재활성화하지 않고 인계를 완료한다. 실제 시각과 데모의 가상 제조 시계는 구분한다.

이전 작업에 복구 메타데이터가 없으면 최초 조회 때 한 번만 스케줄을 부여한다. 생성 시각을 추측해 만료시키지 않는다. 복구 단계가 바뀔 때마다 공개 버전도 증가해 오래된 GET이 최신 화면을 덮지 않게 한다. UI는 GET으로 상태만 읽으며 복구 명령을 자동으로 보내지 않는다.

체험 손님 자리 추가/반환도 같은 저장 작업 큐를 사용한다. 매장 DB 커밋 뒤 답이 사라져도 손님의 자리만 고아 상태로 남기지 않도록 한다. 고객 주문과 혜택 금액에는 영향이 없다.

## 검증과 남는 범위

`test_merchant_http.py`는 실제 별도 프로세스·TCP 요청에서 수락 후 응답 끊김, 3개 저장 지점의 서버 종료, 독립 주문 관리자의 마지막 자리 경쟁을 검사한다. `test_runtime_recovery.py`는 기본 앱 실행 방식에서 수동 recover 요청 없이 복구 및 감독자의 매장 서버 재시작을 검사한다. 기존 로컬 어댑터의 10개 강제 종료 지점 시험도 유지한다. `verify_handoff_browser.py`는 실제 HTTP 화면에서 주문→거절→응답 누락→자동 복구→수령·영수증을 확인한다.

검증한 commit과 원본 로그로 결과를 판단한다. 로컬 Chromium 정책 차단과 미설치 Maven/Docker는 통과로 계산하지 않는다. main 병합 후에는 같은 SHA의 공개 health와 브라우저 결과를 따로 확인한다.

8회 실패 이후 추가 확인은 사용자 수동 재확인 경로다. 실무 운영자 알림/관리 화면, 호스트 장애, DB 영구 유실·손상, 실제 PG/GPS/계정·공유 지갑, 실물 제조 권한까지 구현했다고 주장하지 않는다. 확인 중 두 자리를 잠시 점유하는 가용성 비용은 남는다. 무기한 장애에서도 결국 반드시 성공한다고 보장하지 않는다.
