# Pickup Pact — 멀티 호스트 HA와 DB 유실 복구 설계안

작성일: 2026-10-02
기준 코드: `9cfd70562a85e18dcb842a4a71b333af60ea0a44`
상태: 설계안. 신규 HA 코드, 백업 실행, 장애 전환 또는 복원 시험의 완료 기록이 아니다.

## 1. 목표와 변경 금지 범위

같은 Pickup Pact 주문을 두 가지 장애 뒤에도 설명하고 검증할 수 있게 한다. 첫째는 한 호스트 중단 후 다른 호스트에서 주문·매장·가상 결제 처리를 이어가는 것이다. 둘째는 데이터 파일 유실 후 외부 백업에서 복원하여 주문·매장·결제·혜택과 미완료 작업을 대조하는 것이다.

기존 빠른 체험과 가상 결제 규약은 유지한다. 실제 PG·카드사·실가맹점 연동을 추가하지 않는다. 기존 공개 Render 서비스, main, BrewSlot과 다른 저장소를 이번 설계 작업으로 바꾸지 않는다. 유료 서비스·저장소·가상 머신 생성은 비용과 권한이 승인된 뒤에만 한다. 운영 DB 파일을 파괴하는 시험은 하지 않는다.

성과는 연결 상태 표시가 아니라 실제 장애를 발생시킨 뒤의 복구 결과로 판정한다. 한 컴퓨터의 여러 프로세스나 컨테이너를 실제 멀티 호스트 검증으로 부르지 않는다.

## 2. 직접 확인한 현재 구조

| 위치 | 기준 코드의 동작 | 필요한 변경 |
|---|---|---|
| `demo/route/runtime.py` | 앱 lifespan 안에서 매장·가상 결제·알림 수신 프로세스와 복구 작업자를 실행한다. | HA 모드에서는 각 역할을 독립 실행 단위로 분리한다. |
| `demo/route/store.py` | 주문·명령·체험 설정을 SQLite에 저장한다. 기본 매장 경로와 알림 수신 비밀키도 인스턴스에서 만든다. | 공유 주문 저장소, 명시적 연결 설정, 인스턴스 공통의 관리되는 인증 정보를 사용한다. |

| `demo/route/payments/repository.py` | 승인·확정·해제·멱등 응답·outbox를 별도 SQLite에 원자적으로 기록한다. 주문별 확정 청구 고유 제약이 있다. | 같은 불변조건을 PostgreSQL 저장소의 제약과 트랜잭션으로 보존한다. |

Render에서 조회한 기존 `pickup-pact-demo`는 free 플랜, 인스턴스 1개, main 자동 배포다. 이 서비스의 복제 수나 플랜은 변경하지 않았다. 새 HA 대상 서버·외부 백업 저장소는 아직 배정하거나 생성하지 않았다.

## 3. 대안과 선택

앱만 여러 개 띄우면서 각 서버의 SQLite를 별도로 쓰는 방식은 제외한다. 같은 주문에 서로 다른 상태가 생길 수 있기 때문이다. 공유 파일 디스크에 의존하는 방식도 이번 HA 경로로 택하지 않는다.

설계 기준은 **역할별 서비스 복제 + PostgreSQL HA 클러스터 + 클러스터 밖의 백업**이다. 개발·계약 검증은 기존 공개본과 분리한다. 실제 호스트 시험은 승인된 서버 목록에만 배포한다.

관리형 Render PostgreSQL HA는 별도 배포 대안이지만 기본 시험 구성으로 확정하지 않는다. 공식 문서상 비동기 복제이며 비용도 발생한다. 관리형을 택할 때는 아래 동기 복제 시험과 같은 무손실 조건으로 설명하지 않고 별도 복구 목표와 결과를 기록한다.

## 4. 1번: 멀티 호스트 HA

### 실행과 저장소

설계 기준 데이터 계층은 서로 다른 Linux 호스트 3개에 PostgreSQL 17 데이터 노드와 Patroni, 3구성원 합의 저장소를 배치하는 것이다. 호스트 한 대의 중단을 시험하므로 데이터 노드와 합의 구성원의 장애 영역도 분리한다. PostgreSQL의 세부 릴리스와 이미지 digest는 구현 환경 검증 때 고정한다. 지원 종료 버전이나 개발판을 자동 선택하지 않는다.

앱·가맹점·가상 PG는 각각 적어도 두 호스트에서 실행한다. 복구 작업자도 대체 가능한 형태로 실행한다. 외부 요청 진입점과 내부 서비스 경로 역시 단일 프록시 프로세스에만 의존해서는 안 된다. 실제 배포 명세에는 진입점 장애 전환 방식과 호스트 배치 증거가 필수다. 그 증거가 없는 로컬 구성은 기능 시험일 뿐 HA 통과가 아니다.

한 PostgreSQL 물리 클러스터 안에 주문, 가맹점, 가상 PG의 데이터베이스와 접근 역할을 분리한다. 이는 비용과 공통 시점 복구를 위한 의도적인 물리 인프라 공유다. 세 개의 독립 물리 DB 클러스터라고 주장하지 않는다. 서비스는 자기 데이터만 변경하고, 서비스 사이에는 기존 HTTP와 저장된 작업 프로토콜을 유지한다. 서로 다른 서비스 DB를 하나의 업무 트랜잭션으로 묶지 않는다.

HA 모드는 제안 값 `ha_postgres_v1`로 분리한다. 기존 단일 호스트 SQLite 모드는 유지하되 런타임 표시와 검증 결과를 섞지 않는다. HA 모드에서 DB나 내부 서비스가 끊겼다고 SQLite 모의 성공으로 대체하지 않는다.

### 데이터베이스 전환 원칙

Patroni 동기 모드, strict 동기 복제와 최소 한 대의 동기 대기 노드 확인을 기준으로 삼는다. 서버 역할·동기 상태와 WAL 위치를 확인한 후보만 승격한다. 동기 대기 노드나 합의가 부족하면 쓰기를 제한한다. 가용성을 얻으려고 승인된 내구성 조건을 자동 완화하지 않는다. 손실을 허용하는 수동 강제 승격은 정상 복구 경로가 아니다.

DB 리더 임대가 만료된 노드는 쓰기를 계속할 수 없어야 한다. watchdog 등 실제 플랫폼에서 검증 가능한 fencing을 배포 전제조건으로 삼고, 지원하지 않으면 분할 뇌 방지 검증을 통과시킬 수 없다. 임의로 privileged 권한을 열거나 호스트 보안 정책을 우회하지 않는다.

동기 복제는 모든 장애에서 데이터 유실 0을 보장하는 표현으로 쓰지 않는다. 시험 범위는 단일 호스트 상실이며, 성공 응답이 반환된 작업 집합의 보존을 확인한다. DB 취소·통신 단절로 결과가 불명확한 요청은 별도로 분류해 기존 키로 조회한다.

### 업무 정합성과 역할 분리

- SQLite SQL을 문자열 치환해 PostgreSQL로 보내는 우회 계층을 만들지 않는다. 주문·명령·복구 스케줄·inbox, 매장 예약·명령 영수증, PG 승인·거래·outbox에 저장소 인터페이스와 실제 PostgreSQL 구현을 둔다.
- 요청키의 동일 내용 재실행, 다른 내용 충돌, 주문별 한 번의 확정 청구, 매장 세대·제조 권한, 쿠폰·포인트 한 번 반영을 모두 유지한다.
- 작업자는 DB에서 작업과 임대 버전을 짧은 트랜잭션으로 확보한다. 외부 HTTP 동안 DB 쓰기 잠금을 유지하지 않는다. 여러 작업자가 깨어나도 외부 작업키는 같고, 늦은 응답은 단계·임대 버전을 대조한 뒤 반영한다.
- PG 사용 한도처럼 여러 승인 행을 함께 보는 규칙에는 명시적 동시성 보호를 둔다. 고유 제약 하나로 한도 경합까지 해결했다고 보지 않는다.
- 내부 서비스 URL은 허용된 배포 설정에서만 받는다. 공유 HMAC 키·인증서는 비밀 관리 경로로 공급하고 브라우저·GitHub·증거 파일에 넣지 않는다. 인스턴스마다 무작위 키를 만들어 서로의 알림을 거절하게 두지 않는다.
- 연결 풀은 장애 후 새 리더에 다시 연결한다. COMMIT 중 연결이 끊기면 요청 전체를 새로운 주문·청구 키로 재시도하지 않는다.
- `/health` 생존 여부와 DB·서비스 준비 상태를 분리한다. 노드 ID·역할·연결 가능 여부를 조회할 수 있어도 토큰·DSN은 노출하지 않는다.

## 5. 2번: DB 파일 유실 복구

### 백업 구성

PostgreSQL 물리 기본 백업과 연속 WAL 보관을 사용한다. 주문·가맹점·가상 PG가 같은 물리 클러스터에 있으므로 전체 클러스터를 같은 복구 지점으로 복원한다. 서비스 간 트랜잭션이 진행 중이던 상태는 저장된 작업과 outbox/inbox로 이어간다.

백업은 DB 호스트의 같은 디스크나 같은 소실 범위에 보관하지 않는다. 별도 호스트 또는 승인된 객체 저장소를 사용하고, 암호화·최소 권한·버전 보존을 적용한다. 백업 파일과 복호화 키를 같은 유실 경로에만 두지 않는다. 라이브 서비스 계정에는 백업 전체 삭제 권한을 주지 않는다.

manifest에는 클러스터 식별자, 타임라인, 기준 코드·스키마 버전, 백업 시작/종료 WAL 위치, 필요한 WAL 범위, 파일 크기·해시, 외부 업로드 확인을 남긴다. 업로드 중인 백업을 복원 가능 상태로 게시하지 않는다. 해시·WAL 연속성 검사 뒤 실제 복원과 애플리케이션 대조까지 해야 복구 시험 통과다.

백업 생성·보존 횟수와 저장 공간 제한은 배포 명세의 필수 설정이다. 보존 중인 기본 백업을 복원하는 데 필요한 WAL을 삭제해서는 안 된다. 로그 보관 지연·실패를 감시하고, 아카이브 주기만으로 복구 지점 목표를 달성했다고 판단하지 않는다.

### 유실·오삭제 시험

운영 데이터 삭제 대신 격리된 시험 클러스터의 새 볼륨에서 실행한다. 시험 ID, 테스트 데이터 표시, 허용된 호스트/볼륨 목록과 운영 주소 불일치를 검증한다. 조건이 하나라도 맞지 않으면 파괴 단계를 수행하지 않는다.

첫 시험은 테스트 DB의 데이터 볼륨을 완전히 사용할 수 없게 만든 뒤, 남은 복제본을 사용하지 않고 외부 기본 백업과 WAL만으로 새 클러스터를 복구하는 것이다. 단일 노드 파일 상실 후 다른 복제본으로 전환하는 HA 시험과 구분한다. 두 번째 시험은 잘못된 데이터 변경 이전의 명시적 지점으로 복원하는 PITR 시험이다.

복원은 기존 공개 서비스의 DB 경로가 아니라 새 대상에 수행한다. 복원된 서비스가 옛 결제·매장 서버나 운영 알림 주소를 호출하지 않도록 네트워크와 인증을 격리한다. 옛 클러스터의 쓰기를 차단한 뒤에만 서비스 전환 후보가 된다.

복원 후 옛 타임라인의 늦은 HTTP 요청과 알림이 다시 처리되지 않도록 별도 운영 설정의 복구 세대와 내부 키를 갱신한다. 단, 주문·승인·결제의 기존 멱등 키를 새로 만들어 재청구하지 않는다. 옛 견적은 새 상태 조회 뒤 다시 동의하도록 하고, 복원 전후에 같은 거래를 조회하는 경로와 신규 요청을 구분한다.

### 복원 완료 조건

승인된 마지막 목표 지점까지 복원됐는지 확인하고, 실제 보존된 주문 집합과 그 이후 유실 가능 구간을 보고한다. 백업 이후 기록이 존재하지 않는데 임의로 재생성하지 않는다. RPO는 보관·복원 가능한 마지막 기록으로, RTO는 장애 판정부터 검증 완료와 서비스 재개까지의 관측 시간으로 계산한다. 수치는 측정 전에는 성과로 기재하지 않는다.

정상 수령 주문의 마지막 동의 금액, 청구 횟수·합계, 불필요한 승인 보류, 수령 매장 수, 쿠폰·포인트, 작업키와 저장된 결과를 대조한다. 미완료 주문은 안전한 재개 또는 추가 확인 상태여야 한다. 원본을 읽지 못한 경우를 0원 또는 MATCH로 표시하지 않는다. 현재 가상 시스템 전체를 복구하는 범위이며 실제 외부 PG의 장부까지 과거로 되돌린다고 주장하지 않는다.

## 6. 배포와 기존 데이터

개발·계약 시험, 독립 호스트 시험, 공개 전환을 별도 게이트로 둔다. 기존 무료 공개본은 마지막 게이트 전까지 그대로 유지한다. 실제 호스트 인벤토리·접근 권한·진입점·백업 저장소·월별 비용 상한은 아직 승인된 배포 명세가 아니며, 이를 확보하지 않고 클라우드 리소스를 만들지 않는다.

새 모드의 검증은 우선 합성 신규 체험으로 한다. 기존 SQLite의 진행 중 체험을 묵시적으로 이동시키지 않는다. 이전이 필요하면 모든 작성 역할을 정지·확인한 체크포인트에서 원본을 보존하고, 변환·행 수·키·금액·진행 단계와 영수증을 검증하는 별도 이전 절차를 작성한다. DB 파일 하나만 복사해 여러 저장소가 같은 시점이라고 가정하지 않는다.

기존 `/classic`, `/repair-lab`, JVM/Kafka 및 과거 비교 실험은 별도 경로로 유지한다. 새 HA 판정은 이번에 이식한 고객·매장·가상 PG 경로에만 적용한다. 공개 롤백은 기존 모드로 운영 주소를 되돌리는 일과 새 DB의 데이터를 되돌리는 일을 구분한다. 새 DB에 들어간 거래를 옛 DB에 없는 것으로 처리해서는 안 된다.

## 7. 인수 검증표 — 전 항목 아직 미실행

| ID | 시험 | 통과 기준 |
|---|---|---|
| HA-01 | 서로 다른 앱 인스턴스로 같은 요청 반복 | 동일 주문·동일 결과, 다른 내용의 동일 키는 충돌 |
| HA-02 | 승인/청구 저장 후 응답 유실, 앱 호스트 중단 | 기존 거래로 확인, 중복 청구·혜택 반영 없음 |
| HA-03 | 가맹점 또는 가상 PG 호스트 중단 | 다른 호스트의 해당 역할로 재확인, 로컬 모의 성공 fallback 없음 |
| HA-04 | 주 DB 호스트 강제 중단 | 안전한 후보로 승격, 성공 응답된 작업 보존, 불명확 요청 별도 판정 |
| HA-05 | 한 대의 대기 DB 호스트 중단 | 남은 노드로 동기 조건 회복, 조건을 자동 완화하지 않음 |
| HA-06 | 리더 네트워크 분리·복귀 | 동시에 둘 이상의 쓰기 리더 없음, 옛 리더의 쓰기 차단 |
| HA-07 | 복구 작업자 동시 실행·임대 만료 | 동일 외부 키 사용, 낡은 응답 거부, 다른 주문까지 전역 잠금하지 않음 |
| HA-08 | PG 한도·중복 청구 동시 경합 | 한도 초과 승인과 같은 주문의 두 번째 확정 모두 차단 |
| HA-09 | 고객/매장 다중 탭과 중복·지연 알림 | 주문·제조·수령·금융·혜택 불변조건 유지 |
| HA-10 | 진입점 중단·재연결 | 실제 운영 진입 주소가 단일 프록시 호스트에만 의존하지 않음 |
| DR-01 | DB 데이터 파일 전체 유실 | 외부 백업+WAL만으로 새 대상에서 복원, 원본 복제본 사용 여부 명시 |
| DR-02 | 오삭제 전 지점 복원 | 선택한 지점과 복구된 거래 집합 일치 |
| DR-03 | WAL 누락·파일 변조·업로드 미완료 | 유효 백업으로 승인하지 않고 안전하게 실패 |
| DR-04 | 백업 저장소 접근 불가·용량 한계 | 실패를 감지, 불완전 백업을 성공 처리하지 않음 |
| DR-05 | 진행 중 매장 변경·청구 중 복원 | 각 원장의 알려진 결과로 재개, 새 멱등 키로 재청구하지 않음 |
| DR-06 | 복구 전 늦은 명령·알림 재도착 | 옛 세대 통신 차단, 기존 거래 조회·재개는 가능 |
| DR-07 | 복호화 키·설정 복원 | 승인된 경로로 복원 가능, 비밀이 증거 JSON에 없음 |
| DR-08 | 운영 주소·비시험 볼륨을 대상으로 지정 | 파괴·복원 명령을 수행하지 않고 거부 |
| REG-01 | 기존 단일 호스트와 신규 모드 회귀 | 기존 테스트 제외·단언 완화 없이 각각 반복 성공 |
| UX-01 | 같은 데모의 장애·복구 결과 | 확인 중·유실 가능 구간·실측 복구 시간을 정확히 표시 |

각 호스트 장애와 복원 시나리오는 독립 초기 상태에서 최소 3회 반복한다. 여러 번 실행한 성공만 골라 실패를 지우지 않는다. 실패 로그와 최종 수정 후 결과를 구분한다. 환경·노드/호스트 ID·코드 SHA·역할 배치·DB 복제 상태·백업 manifest·복구 전후 원장·RPO/RTO를 남긴다. 네트워크 주소와 자격증명은 공개 증거에서 제거한다.

## 8. 착수 순서와 검토 경계

공통 저장소 인터페이스와 PostgreSQL 계약을 먼저 정리하고, 기존 가상 PG·매장 프로토콜을 이식한다. 이후 역할 분리·복구 작업자 경합을 검사한다. 같은 저장 구조 위에서 HA 배치와 백업·복원 경로를 연결한다. 마지막으로 독립 호스트 장애, 전체 DB 유실, 원본 대조와 기존 UI 회귀를 수행한다.

현재 단계의 산출물은 이 설계안과 현 구조의 영향 분석이다. 실제 구현 계획·제품 코드·유료 인프라·배포는 이 문서의 작성과 구분한다. 배포 자원과 비용을 승인받기 전에도 설계와 로컬 계약 구현 준비는 가능하지만, 이를 실제 멀티 호스트 실행 성공으로 세지 않는다.
