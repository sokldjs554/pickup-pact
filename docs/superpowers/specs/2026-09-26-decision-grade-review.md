# Pickup Pact: 검토 가능한 매장 변경

요청: 현재 부족점을 실제 코드/화면에서 보완 → 변경점과 증거를 사용자에게 제시 → 그 이후 지원서 작성. 이번 작업에서 지원서/포트폴리오는 작성하거나 공개하지 않는다.

기준 main 8dee63822020d2217a91882cedaf9badf9988f90, tree 5d00b7e03debaa1b449d4d5f00bd467e30c1e6d6. 원본 ZIP 모드를 복원한 트리가 일치한다.

## 설계
1. 새 체험에만 versioned transfer agreement를 도입한다. 참여 그룹, 양 매장 허용, 명시적인 음료 용량/온도/옵션 적합성을 서버가 검증한다. 맛/브랜드가 같다고 주장하지 않는다. 미가입 매장은 최초 주문은 가능하지만 이관은 불가하다. 기존 보존 체험은 legacy 범위로 남긴다.
2. quote_id가 상품/참여/금액/부담 주체 조건을 함께 묶는다. 고객은 변경 확인창에서 조건을 보고 해당 견적을 확정한다. 변경 이벤트에 수락한 조건을 보존한다. 수령 시 고객 현금+플랫폼 쿠폰/포인트 부담=매장 모의 수취액이라는 균형을 검사한다. 실제 PG/가맹점 합의는 없다.
3. 비교에 '새 자리 확보 후 재주문'을 추가한다. 동일 내구성 엔진/매장 프로토콜을 재사용하면서 새 주문 ID와 재승인을 만드는 기준이다. 같은 안전 절차를 적용하면 주문 보존에서 동률일 수 있음을 공개한다. 독립 구현 검증이나 경쟁 앱 구현이라고 부르지 않는다.
4. 비교의 임시 저장소를 실행당 한번 초기화하되 각 case/policy의 world/journey는 분리한다. durable SQLite 설정은 낮추지 않는다. 초기화/실행 시간과 원본 결과를 남긴다.
5. 첫 화면에서 거절 시 주문 보존과 응답 누락 자동 확인을 가장 먼저 전달한다. 정책/제약을 접어서 제공하고 화면에서 바뀐 terms와 모의 정산을 확인할 수 있게 한다. 자동 갱신이 미확정 사용자 선택을 지우지 않게 한다.
6. 핵심 응답의 명시적 모델(주문/혜택/작업/비교/정산/조건)과 명세 스냅샷을 보완한다. 반례→수정→회귀, 실제 HTTP/브라우저, exact SHA CI/공개 배포는 각각 별도 증거다.

## 범위/정직성
고객 인터뷰, 점주 합의, 실매출, 실물 PG, HA 운영 및 지원자의 코드 이해를 구현만으로 증명하지 않는다. 검증할 질문/실험 조건을 프로젝트 문서로 제공하되 사람의 답변을 생성하지 않는다. MIT 추가 없음. 기존 금융/복구/영상은 유지하며 앱 변경 이후 구영상은 기준 SHA가 다른 이전 녹화라고 표시한다.
