# 매장 변경 전체 감사와 실제 실행 경계

사용자가 승인한 목표: 주문·혜택·매장 변경·제조·수령·영수증과 실패 복구를 전체 검토한다. 발견한 요구 누락과 오류를 고친 뒤 원격 CI, 실제 HTTP 브라우저, 정확한 main 공개 배포, 같은 앱의 영상·포트폴리오를 확인한다. 정해진 세 항목 외의 오류도 제외하지 않으며, 무관한 새 제품 기능은 추가하지 않는다.

## 처리 원칙
주문 의도를 먼저 보관한다. 기존 매장을 잠시 고정하고 새 자리를 확보한 뒤 COMMIT을 저장한다. COMMIT 이전의 오래된 작업만 ABORT를 저장하고 새 자리 반환 및 기존 제조 재개를 확인한다. COMMIT 이후에는 시간 초과만으로 원래 매장을 활성화하거나 새 자리를 해제하지 않는다. 응답이 없는 것과 거절된 것은 다르다.

## 복구
사용자가 페이지를 닫아도 서버가 저장된 작업을 조회한다. 다음 실행 시각과 실패 횟수는 작업에 남긴다. 재시도는 3초에서 시작해 최대 30초 간격으로 늘고, 8회 실패하면 자동 재시도를 멈추고 추가 확인 상태로 둔다. 이 상태를 주문 성공/취소로 바꾸지 않는다. 명시적인 재확인은 같은 작업을 사용한다. 시간 기준은 서버 경과 시간이며 가상 쿠폰/픽업 시계와 별개다. 변경 결정 전 대기 한도는 45초다.

## 통신과 공개 환경
가상 매장 역할은 별도 프로세스의 실제 HTTP 서버이며 매장별 독립 SQLite 파일을 사용한다. 내부 토큰과 0.8초 요청 timeout, 요청 크기와 명령 타입 제한을 사용한다. 수락 저장 뒤 응답을 끊는 체험은 해당 요청 식별자에 한 번만 적용한다. 공개 URL로 내부 서버를 노출하지 않는다. 단일 호스트·임시 디스크의 한계와 실제 PG/GPS/가맹점 미연동을 숨기지 않는다.

## 전체 검토 범위
정상 주문, 예산·쿠폰·포인트, 거절·동시성·오래된 견적, 단계별 강제종료, worker 재시작, 저장 형식 업그레이드, HTTP 타입 오류·응답 누락·프로세스 재시작, 프런트 재조회 경쟁, 기존 고객/점주/복구 기능, 명세·문서·영상 일치. 운영자가 확인해야 할 상태를 단순 성공으로 축소하지 않는다.

## 완료 조건
해당 수정 tree의 전체 Python·JS·JVM·Docker·SQL/인프라 검증, 실제 HTTP 브라우저 반복, 원격 main SHA와 공개 SHA 일치 확인. 미검증/실패는 별도 기록. 영상은 공개된 앱을 직접 촬영한 경우에만 공개 증거로 부르며, 이전 영상을 새 기능의 증거로 사용하지 않는다. 기능 검증과 경쟁 서비스 우위 입증은 다른 주장이다.
