# 시간 중심 커피 주문 · Pickup Pact Route

## 사용자의 목표
기존 내부 정합성 작업대가 아니라 패스오더 같은 제품과 비교했을 때 고객이 즉시 이해하는 차별적인 제품 경험을 구현한다. 주문 예약, 적립, 같이 주문, 단순 타임라인은 핵심 차별점에서 제외한다. 이번 요청은 설계 설명이 아니라 직접 다시 제작하는 것이다.

## 제품 결정
“9시 회의 전에 커피를 들고 도착하고 싶다.” 고객은 음료 조건, 목적지, 마감, 예산, 허용 우회를 입력한다. 서버는 거리만이 아니라 제조 대기와 목적지까지의 경로를 함께 계산한다. 주문한 매장에 문제가 생기면 제조 전, 고객 승인 아래 동일 주문을 다른 매장으로 이관한다. 품목/우유/디카페인 조건을 몰래 바꾸지 않는다. 한 주문의 계획·매장 상태·모의 결제·수령 코드·영수증을 같은 저장 데이터에서 읽는다.

## 고려한 대안
1. 예약·같이 주문 확장: 공개 패스오더 기능과 겹쳐 제외.
2. 사고 재현/복구 대시보드: 고객의 핵심 과제 해결이 약해 주인공에서 제외.
3. 목적지 마감 기반 주문 + 제조 전 매장 이관: 채택. 네트워크 매장 간 단일 주문 의도라는 제품 차이와 도메인 상태/가격/동시성 문제를 동시에 보여준다.

## 경계와 불변식
- 가상 동네, 합성 매장, 가상 시계. 실제 지도/GPS/가맹점/결제 연동 없음. 예측 시간은 모델 계산이며 실제 SLA가 아니다.
- Dijkstra 경로 탐색 + 준비 시간 + 목적지 잔여 이동 + 1분 여유; 제한 위반 후보는 제외 이유 공개.
- 매장 이관은 RESERVED 상태만. PREPARING/READY/PICKED_UP에서는 금지. 제조 전 동시 이관/제조 시작은 한 결과로 수렴.
- 예산 초과, 메뉴/우유/디카페인 불일치, 오래된 quote/version 거부.
- 모의 결제 승인은 한 주문에 한 번. 이관 시 차액 조정 내역. 수령 시 capture 한 번. 실제 돈 이동 없음.
- SQLite BEGIN IMMEDIATE로 한 데모 세션의 명령·이벤트·금액 원자성, 버전/멱등키 검증. 분산 원자성 주장 금지.
- 기존 루트 화면은 /classic으로 이동; 기존 API와 /repair-lab 보존. 새 루트는 소비자 제품. 기존 테스트는 기존 진입 경로만 수정, 단언 유지.
- 실패한 API 후 성공 안내 금지. 새로고침/다른 뷰에서도 같은 주문. 좁은 모바일 화면 지원. MIT 문구/라이선스 추가 금지.

## 완료 증거
실제 HTTP 브라우저에서 조건 변경→경로 계산→주문→매장 혼잡→다른 매장으로 이관→매장 제조→1회 수령→같은 주문 영수증 확인. 예산 부족/엄격 조건/제조 후 이동 금지/오래된 계획/동시 요청/재시작 시험. 기존 테스트 반복. 새로운 커밋/CI/배포는 별도로 확인, 실행 못한 것은 명시한다.
