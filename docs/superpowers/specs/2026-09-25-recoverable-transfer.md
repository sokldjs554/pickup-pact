# 주문을 잃지 않는 매장 변경

사용자 승인: 매장 이동의 실패·경합·재시작을 실제 코드로 처리하고, 취소 후 재주문과 비교한다. 새 주문 앱으로 갈아엎지 않고 기존 고객/혜택/매장/영수증에 연결한다.

## 불변식과 구현 범위
- 변경 상대가 수락하기 전에는 원래 주문과 혜택을 버리지 않는다.
- 매장별 독립 SQLite DB와 주문 coordinator DB를 사용한다. 같은 체험 회차의 여러 주문은 동일 제조 자리를 공유한다. 실제 가맹점/PG/운영 계정/원격 네트워크 서비스는 아니다.
- 주문 의도/단계는 원격 역할의 DB 변경보다 먼저 저장한다. 재시작은 저장된 작업 ID로 진행하며, 단계 사이 전역 트랜잭션을 주장하지 않는다.
- 이동 순서: 원래 제조 잠금 → 새 매장 자리 보류 → commit 결정 → 원래 자리 해제 → 새 매장 활성화 → 주문/혜택 확정. commit 전 거절은 보류 해제 후 원래 주문 복원. commit 뒤 응답 불명은 완료로 위장하지 않고 재확인한다.
- 같은 주문을 동시에 두 매장에서 제조할 수 없다. 전송 ID/세대 검사를 두어 옛 요청이 새 주문 소유권을 덮지 못한다.
- 모든 신규 주문은 이 경계를 사용한다. 기존 저장 세션은 이전 경계를 명시하고 새 체험으로 안내한다. 금액 계산/쿠폰 정책/원본 이벤트의 기존 의미를 유지한다.
- fault는 체험 회차의 다음 이동에만 적용된다. 다른 사용자의 회차를 변경하지 않는다. 화면의 합성 손님은 동일한 매장 접수 명령과 DB 제약을 사용한다. 두 완전한 주문의 경합은 별도 자동 시험에서 확인한다.
- 비교에는 유지만 아니라 취소 후 재주문도 포함한다. 재주문도 올바른 멱등키/조건 확인을 사용한다. 알려진 실패를 무시하도록 일부러 약화하지 않는다. 시간/시장 우위로 확대하지 않는다.

## 화면
기존 주문 카드에 '다른 매장이 받아줄 때만 바꿔요', 실제 단계, 기존 주문 보존 여부, 다음 '다시 확인하기'를 표시한다. 거절/응답 누락/다른 손님 주문은 상황 바꿔보기 아래에 둔다. 숫자와 결과는 서버 응답에서 읽는다. 모바일 지원. 기존 할인 상실과 추가금 동의는 유지한다.

## 검증
기존 259개 baseline. 신규 shared last-slot 경합, 제조/이동 동시 요청, 동일키 24회, 다른키 충돌, commit 전후 프로세스 강제종료/재시작, target 거절과 rollback, 이전 세대 요청, 포인트/쿠폰/영수증, API validation, 실제 HTTP Chromium(허용되는 환경) 및 기존 regression. 실행하지 못한 검증과 배포 제한은 통과로 세지 않는다.
