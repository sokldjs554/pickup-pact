## 1. 목표와 범위

면접관이 하나의 주문을 따라가며 고객 화면, 실제 HTTP로 연결된 가상 매장, 별도 결제 서버의 처리 결과를 확인하게 한다. 핵심은 버튼이나 기술 이름을 늘리는 것이 아니라 **“다른 서버가 처리했는데 답만 사라졌을 때, 새 주문이나 새 결제로 덮지 않고 기존 거래를 확인한다”**는 점을 보여주는 것이다.

기존 빠른 시작, 직접 조건 선택, 제조 전 매장 변경, 차액 동의, 쿠폰·포인트, 수령·영수증을 유지한다. 추가 대상은 다음 네 가지다.

1. 기존 가상 가맹점 HTTP 연동을 보여주는 두 매장의 단말 화면.
2. 주문 DB와 분리된 프로세스·DB를 가진 가상 결제 서버.
3. 승인·결제 확정·승인 해제의 응답 누락과 중복 알림 복구.
4. 주문·매장·결제 기록을 조회해 대조하는 마지막 결과 화면.

이번 범위에서 실제 PG·카드사 API, 실제 카드번호·CVC·개인정보, 유료 서비스 생성, 실제 가맹점 계정, 새 포트폴리오 저장소를 추가하지 않는다. BrewSlot은 변경하지 않는다. 기존 JVM/Kafka 서비스와 새 데모를 하나의 운영 경로라고 설명하지 않는다.

## 2. 기존 코드에서 확인한 연결 지점

아래 내용은 기준 커밋을 읽은 결과다. 확장 기능의 테스트 통과를 뜻하지 않는다.

| 파일 | 현재 역할 | 설계에 미치는 영향 |
|---|---|---|
| `demo/route/store.py` | 주문 상태·혜택·모의 승인/결제 이벤트를 같은 저장소에 기록한다. | 외부 결제 확인 없이 생성한 모의 이벤트를 새 결제 서버의 증거로 사용하면 안 된다. |
| `demo/route/durable_operations.py` | 후보 주문을 먼저 만들고 매장 단계별 결과를 확인한 뒤 후보를 최종 반영한다. | 새 결제 단계와 복구 결정도 영속 작업 기록에 포함해야 한다. |
| `demo/route/merchant_http.py` | 별도 매장 프로세스와 실제 HTTP 통신을 하고 응답의 주문·세대를 대조한다. | 가맹점 연동을 재구현하지 않고 기존 통신·세대 차단 규칙을 재사용한다. |
| `demo/route/runtime.py` | 한 호스트에서 매장 프로세스와 복구 작업자를 실행한다. | 결제 프로세스 감독을 추가하되 외부 결제 모드가 내부 모의 기록으로 자동 대체되지 않게 한다. |
| `demo/route/recovery_worker.py` | 결정 전 45초 기한, 최대 8회 실패, 3~30초 재시도와 추가 확인 상태를 관리한다. | 매장 전용 보상 단계를 결제 단계에 그대로 적용하지 않는다. |
| `demo/route/api.py` | 같은 출처 요청·엄격한 입력·견적·버전 검사를 한다. | 새 결제 선택·대조 응답과 인증된 서버 알림을 별도 계약으로 정의한다. |
| `demo/route/guide-flow.js` | 현재는 `order` 유무를 미완료 작업보다 먼저 판단한다. | 최초 승인 응답이 불명확한 상태에서 “다시 주문”을 권하지 않도록 대기 상태를 우선한다. |

특히 현재 `resume()`은 `BEGIN IMMEDIATE` 안에서 단계의 HTTP 요청을 수행한다. 결제까지 넣는 새 프로토콜에서는 **요청 계획 저장 → DB 트랜잭션 종료 → 외부 I/O → 작업·단계 버전 대조 후 결과 반영**으로 분리한다. 이전 프로토콜을 함께 바꾸는 광범위한 리팩터링은 하지 않는다.

## 3. 대안과 선택

| 대안 | 얻는 것 | 한계 | 선택 |
|---|---|---|---|
| 현재 내부 모의 결제에 화면만 추가 | 구현 변화가 작다. | 외부 승인 저장 후 응답 유실을 검증하지 못한다. | 제외 |
| 독립 가상 결제 서버 + 기존 매장 연동 | 장애 시점, 저장 기록, 중복 처리와 재시작을 재현할 수 있다. | 실제 결제업체 계약·동작을 증명하지 않는다. | **선택** |
| 외부 PG 테스트 환경을 기본 체험에 연결 | 해당 업체의 테스트 API 연동을 보여준다. | 계정·키가 필요하고 모든 장애 시점을 통제할 수 없다. | 후속 별도 범위 |

결제 프로토콜은 이 데모의 가상 규약이다. 아래 승인 보류, 새 금액 재승인, 수령 시 확정을 일반적인 국내 카드 결제 API의 기능이라고 주장하지 않는다.

## 4. 화면과 체험 흐름

### 4.1 첫 화면

큰 시작 버튼은 하나로 유지한다. 제안하는 설명은 다음과 같다.

> 주문한 카페가 밀렸나요? 다른 참여 매장에서 이어받고, 연결이 끊겨도 주문과 결제부터 확인해요.

기존 금액·혜택 안내에 `가상 카드 사용 · 실제 결제 없음`만 추가한다. 카드번호 입력 폼은 만들지 않는다. 고정 테스트 토큰 `demo-approved`와 `demo-declined`를 상세 설정에서 선택하며, 기본은 승인 가능한 가상 카드다.

기존 가이드 시나리오와 결제 장애 시나리오는 같은 제품·같은 결제 경로를 사용한다. 결제 문제는 상세한 “문제 상황 골라보기”에서 선택할 수 있게 하고, 모든 장애를 한 회차에 강제로 겹치지 않는다. 기본 주문 시작 클릭만으로 승인 누락 시나리오를 선택할 수 있는 프리셋도 제공하되 홈페이지의 주 버튼 수를 늘리지 않는다.

### 4.2 고객과 가맹점

고객은 현재 안내처럼 다음 행동을 하나씩 수행한다. 상단 단계 번호와 아래 단계 번호가 겹치지 않게 **주문 → 변경 → 확인 → 제조 → 수령 → 결과**로 통일한다.

가맹점 탭에는 원래 매장과 새 매장의 상태를 나란히 보여준다. 각 상태는 매장 HTTP 조회에서 가져오고 다음 항목을 표시한다.

- 주문 번호, 매장명, 주문 세대.
- 접수/자리 보류/변경 때문에 일시 중지/제조/준비/수령/취소.
- 마지막으로 확인한 명령과 그 명령의 매장 처리 결과.
- 지금 제조 가능한 매장. 다른 매장에서 제조할 수 없는 이유.

단말의 버튼은 주문 조정 서버의 검증을 거쳐 기존 매장 명령으로 이어진다. 브라우저가 내부 매장 API나 DB를 직접 쓰게 하지 않는다. 별도 탭으로 보더라도 같은 체험의 권한 범위만 가진다. 실제 POS 연동·가맹점 관리자를 인증한 서비스라고 표시하지 않는다.

### 4.3 결제 상세

기본 화면에는 `승인 확인 중`, `승인 보류`, `결제 확정 중`, `결제 확정`, `승인 해제 확인 중`, `추가 확인 필요`를 표시한다. 응답이 없을 때 `실패` 또는 `결제 0건`이라고 단정하지 않는다.

접힌 상세 영역에는 결제 시도 ID, 승인 ID, 실제 가상 결제 DB의 거래 목록, 최종 청구액, 남은 승인 보류액과 마지막 확인 시각을 보여준다. “서버가 확인 중”이라는 문구만 띄우고 성공으로 넘어가는 타이머는 사용하지 않는다.

### 4.4 마지막 결과

큰 결과는 네 가지로 제한한다.

| 항목 | 정상 수령의 표시 예 | 판정 근거 |
|---|---|---|
| 주문 | 같은 주문 번호 유지 | 최초·최종 주문 ID |
| 매장 | 수령 매장 1곳 | 매장별 상태·처리 영수증 |
| 결제 | 의도하지 않은 중복 청구 없음 | 모든 관련 승인·확정 거래와 합계 |
| 혜택 | 1,000P 한 번 사용, 32P 적립 | 주문 혜택 원장과 결제 확정액 |

결과 상태는 `일치`, `확인 중`, `불일치`, `자료를 읽지 못함`으로 구분한다. 매장이나 결제 서버를 읽을 수 없으면 초록색 “문제 없음”을 보여주지 않는다. 세부 증거는 접어서 보이고, 증거 JSON은 사용자가 명시적으로 저장할 수 있다. 민감한 인증 토큰은 포함하지 않는다.

화면의 이해도는 별도 평가 대상이다. 처음 보는 사람이 짧게 보고 무엇이 보호되는지 설명할 수 있는지, 별도 설명 없이 수령 결과까지 진행할 수 있는지 관찰한다. 실제 평가 전에는 “면접관 누구나 한눈에 이해했다”는 문구를 쓰지 않는다.

## 5. 실행 구조와 데이터 소유권

- 공개 앱 프로세스: 주문·견적·동의·혜택·영속 작업 기록과 UI를 관리한다.
- 기존 가상 매장 프로세스: 매장별 독립 SQLite 파일과 매장 명령 결과를 관리한다.
- 신규 가상 결제 프로세스: 별도 SQLite 파일에서 승인·확정·해제 및 전송할 알림을 관리한다.
- 서버 복구 작업자: 고객 페이지와 무관하게 저장된 다음 단계를 수행한다.

한 호스트 안의 프로세스·DB 분리다. DB 파일을 보존한 프로세스 재시작을 검증한다. 호스트나 DB 파일 전체 유실, 배포 때 임시 디스크 초기화, 다중 호스트 고가용성은 복구 범위가 아니다. 프로세스 재시작 성공을 영구 저장 서비스 운영으로 설명하지 않는다.

가상 결제의 판매 주체는 `DEMO_PLATFORM` 하나로 고정한다. 주문을 다른 가상 매장으로 옮기는 것은 같은 플랫폼 안의 수령·정산 대상 변경이다. 카드사 가맹점번호를 다른 사업자로 옮기는 기능이 아니다. 매장별 정산은 기존 가상 비용 부담 규칙을 사용하고, 카드 청구액과 매장 수취액이 다를 수 있는 쿠폰·포인트 부담을 함께 표시한다.

## 6. 결제 정책 — 금액만 덮어쓰지 않는다

### 6.1 최초 주문

견적과 혜택을 검증한 뒤 안정적인 주문 ID·승인 ID·작업 ID를 먼저 저장한다. 가상 결제 서버의 승인을 확인하고 매장 접수를 진행한다. 두 결과가 확인된 뒤에만 확정 주문과 혜택 보류를 반영한다.

승인 후 매장 접수가 거절되면 그 승인을 해제하고 정리 결과를 확인한다. 승인 응답이 불명확하면 신규 주문이나 신규 승인 ID를 만들지 않는다. 주문 미확정 상태에도 `pending_order_id`를 노출하여 같은 작업을 추적하게 한다.

### 6.2 매장 변경과 금액 변화

원래 매장을 잠시 고정하고 새 자리 확보까지 확인한다. 가격이 같으면 기존 승인을 재사용한다. 가격이 다르면 고객이 동의한 새 금액으로 **새 승인**을 만들고, 기존 승인은 변경 결정 전까지 유지한다.

예: 기존 승인 2,800원 → 새 승인 3,200원 → 변경 결정 저장 → 기존 매장 정리·새 매장 활성화 → 이전 승인 2,800원 해제 → 최종 수령 때 3,200원 확정.

두 승인이 잠시 함께 존재할 수 있다. 이는 확정 청구 두 번과 다르지만, 가상 사용 가능 한도를 일시적으로 줄인다. 이를 UI와 증거에 숨기지 않는다. 새 승인에 필요한 한도가 부족하면 변경을 거절하고 기존 주문·승인을 유지한다. 기본 성공 카드의 가상 한도는 이 과정을 수용하게 하고, 한도 부족 반례는 별도 테스트에 포함한다.

변경이 거절되거나 결정 전 중단되면 새 승인만 해제하고 새 자리를 정리한 다음 원래 매장을 다시 활성화한다. 기존 승인을 먼저 없애지 않는다. 새 승인 결과나 해제가 불명확하면 확인 중으로 남기며, 원래 주문을 다시 만들지 않는다.

**최종 승인 이력이 2건 이상일 수 있으므로 “모든 기록이 1건”을 목표로 삼지 않는다.** 정상 수령의 목표는 최종 동의 금액 3,200원에 맞는 확정 청구, 중복 확정 없음, 더 이상 필요하지 않은 승인 보류 0원이다.

### 6.3 수령

수령 코드·현재 매장·주문 세대·준비 완료 상태를 먼저 검증한다. 활성 승인을 결제 확정하고, 확인된 뒤 매장 수령 명령을 처리한다. 둘 다 확인된 뒤 주문의 수령 완료와 포인트 사용·적립을 한 번 반영한다.

결제는 확정됐지만 매장의 수령 응답만 없으면 `결제 확인됨 / 매장 수령 확인 중`이다. 다시 청구하거나, 음료 전달 여부를 모른 채 자동 환불하지 않는다. 영속 작업과 매장 처리 기록으로 재확인한다. 알려진 충돌도 기록을 확보하지 못한 동안에는 추가 확인 대상으로 남긴다.

### 6.4 취소

이번 고객 취소 범위는 기존처럼 제조 전이다. 매장의 취소 결과와 활성 승인 해제를 모두 확인해야 취소 완료와 혜택 복원을 표시한다. 그 전에는 `취소 확인 중`이다. 해제 응답이 유실됐다고 새 해제를 무한히 만들거나 혜택을 여러 번 복원하지 않는다.

수령 후 환불·부분 환불·차지백 화면은 이번 범위에 넣지 않는다. 승인 해제를 환불이라고 부르지 않는다. 실제 청구 후 반품이나 가맹점 분쟁은 별도의 정책이 필요한 후속 범위다.

## 7. 단계별 복구 규약

| 작업 | 정상 경로 | 실패·불명확 결과의 원칙 |
|---|---|---|
| 최초 주문 | `PAY_AUTHORIZE → ADMIT → FINALIZE` | 승인 거절이면 매장 호출 없음. 매장 거절이면 `VOID_NEW_AUTH`를 확인한 뒤 종료. |
| 매장 변경 | `FREEZE → HOLD → PAY_AUTHORIZE_REPLACEMENT → DECIDE → RELEASE_SOURCE → ACTIVATE → VOID_OLD_AUTH → FINALIZE` | 같은 금액이면 재승인·이전 승인 해제를 건너뛰되 이유를 저장. 결정 전 실패는 새 승인/자리 정리 후 원래 주문 복원. |
| 제조 시작·준비 | 기존 `START / READY` | 유효한 활성 승인과 미확정 작업 없음도 확인. |
| 수령 | `PAY_CAPTURE → CLAIM → FINALIZE` | 청구·수령의 알려진 성공을 각각 저장하고 미확정 단계만 재조회. |
| 제조 전 취소 | `CANCEL → PAY_VOID → FINALIZE` | 한쪽만 확인된 상태는 취소 완료가 아님. |

`DECIDE`의 영속 `COMMIT` 이후에는 임의로 원래 매장을 다시 활성화하지 않는다. `ABORT`를 저장한 뒤에는 늦게 도착한 성공 응답이 정상 변경으로 되살릴 수 없다.

모든 외부 호출에 `world_id, order_id, operation_id, phase, payment_revision`을 묶는다. 작업 단계의 키는 처음 저장한 값을 재사용한다. 동일 키·다른 내용은 409로 거절한다. 클라이언트가 매번 다른 요청키를 주더라도 같은 승인 및 같은 주문에 대한 전체 금액 확정은 결제 DB의 거래 상태와 고유 제약으로 한 번만 허용한다.

### 7.1 “조회 결과 없음”도 자동 실패가 아니다

응답 유실 뒤 거래 조회가 404라고 해서 원래 요청이 이후에도 처리되지 않을 것이라고 가정하지 않는다. 승인 요청의 확정 결과를 동일 키 재조회·재전송으로 확보하고, 이미 중단하기로 결정했으면 승인 확인 후 같은 승인만 해제한다. 이를 해결하지 못하면 추가 확인으로 남긴다. 늦은 승인 결과와 해제 작업은 같은 승인 ID의 저장된 최종 상태로 충돌을 차단한다.

결제 DB는 해제되거나 확정된 승인 ID를 새 요청키로 다시 승인 상태로 되돌리지 않는다. 동일한 승인 요청의 과거 응답 재전송과 현재 거래 상태 조회는 별도로 구분한다.

### 7.2 재시도·버전·타임아웃

기본 재시도는 기존 3초 시작·최대 30초·8회 실패 정책을 사용한다. 45초는 결정 전 중단 판단의 기준이지, 외부 서버가 처리하지 않았다는 증거가 아니다. 결정 이후나 청구 여부 불명확 작업을 이 기한으로 취소하지 않는다.

HTTP 호출 동안 전역 주문 DB 쓰기 잠금을 잡지 않는다. 저장한 단계 버전으로 결과 반영을 제한한다. 동시에 깨어난 복구 작업자가 같은 외부 명령을 보내도 외부 키는 같고, 낡은 결과는 새 단계·세대를 덮지 못한다. 이 규칙은 실제 동시 호출 테스트로 확인한다.

재시도 한도 초과는 `REVIEW_REQUIRED`다. GET·새로고침만으로 재시도 횟수를 초기화하거나 성공 상태로 바꾸지 않는다. 별도의 제한된 재확인 명령만 재시도를 허용한다. 무기한 장애를 반드시 자동 복구한다고 설명하지 않는다.

## 8. 독립 가상 결제 서버의 계약

내부 서버는 loopback에만 바인딩한다. 인증키는 서버에만 두고 브라우저·GitHub·증거 JSON에 넣지 않는다. 임의 URL, 라이브 PG 키, 외부 카드정보를 입력받지 않는다.

### 8.1 최소 API

| API | 목적 |
|---|---|
| `POST /v1/authorizations` | 안정적인 승인 ID와 가상 카드 토큰으로 금액 보류 |
| `POST /v1/authorizations/{id}/capture` | 승인한 전체 금액을 한 번 확정 |
| `POST /v1/authorizations/{id}/void` | 아직 확정하지 않은 승인 해제 |
| `GET /v1/operations/{operation_key}` | 원래 명령의 확정 응답 조회 |
| `GET /v1/orders/{world}/{order_id}` | 해당 주문의 전체 승인·확정·해제 기록과 단조 증가 revision 조회 |

필수 공통 필드는 `world_id`, `order_id`, `operation_key`, `authorization_id`, `amount_krw`, `currency=KRW`, `payment_revision`, `quote_fingerprint`다. 승인에서는 `card_token`도 받는다. 금액은 양의 정수이고 bool·실수·음수는 거절한다. 브라우저가 정한 금액이 아니라 저장된 서버 견적을 사용한다. 전체 금액 0원 주문은 `NO_CHARGE`로 명시하고 카드 승인/확정을 보내지 않는다.

결제 상태는 `AUTHORIZED → CAPTURED` 또는 `AUTHORIZED → VOIDED`다. 승인 거절은 별도 명령 결과 `DECLINED`이며 성공 승인 행을 만들지 않는다. `UNKNOWN`은 조정 서버의 인지 상태이지 결제 서버가 금융 실패를 확정한 상태가 아니다.

### 8.2 저장 모델

- `payment_authorizations`: 승인 ID, 세계/주문, 견적·revision, 금액, 통화, 카드 토큰, 상태, 확정·해제 참조, 생성·수정 시각.
- `payment_commands`: 작업키 고유 제약, 요청 fingerprint, 결과 JSON. 같은 키의 효과·결과를 같은 로컬 트랜잭션에 저장.
- `payment_transactions`: 고유 거래 ID, 승인 ID, 종류, 금액, 주문, 처리 순번. 금융 증거의 원본.
- `payment_outbox`: 고유 event_id, 거래·revision, 원본 본문, 전송 상태·다음 시각·횟수.
- `payment_faults`: 체험 세계와 정확한 작업키에 묶인 1회성 응답 유실·중복 전달 설정.
- 주문 DB의 `payment_inbox`: 인증된 알림의 event_id 고유 제약과 본문 해시. 중복 전달을 두 번 적용하지 않음.

이번 프로토콜은 전체 금액 확정만 지원하므로 확정 거래에 승인별 고유 제약과 `(world_id, order_id)`별 고유 제약을 모두 둔다. 재승인 이력이 여러 개여도 주문의 확정 청구는 하나만 존재한다. 승인 금액과 요청 금액은 PG가 대조하고, 현재 동의된 활성 승인·revision 및 수령 단계는 주문 조정 서버가 저장된 작업으로 검증한다. PG가 주문 DB를 직접 읽어 검증한 것처럼 설명하지 않는다. 원래 승인에 대한 청구 요청은 매장 변경 단계에서 아예 발행하지 않으며, 수령 작업 이후에는 변경·취소를 허용하지 않는다. 이 순서와 지연 요청의 안전성을 T-13~T-16으로 검증한다.

### 8.3 서버 알림

결제 서버는 금융 상태와 outbox 이벤트를 같은 트랜잭션에 저장한다. 알림이 유실돼도 거래 조회로 복구할 수 있게 한다. 알림 수신은 별도 내부 router에서 원문 크기·HMAC 서명·전달 시각·event_id·주문 결합을 검증한다. 외부 Origin 검사를 우회하도록 기존 고객 router의 보호 규칙을 느슨하게 하지 않는다.

알림은 결과 재확인을 깨우는 신호다. 브라우저에서 success=true를 보내거나, 서명이 맞는 오래된 알림이 최신 해제 결과를 덮을 수 없다. event_id의 원본 본문 해시가 다르면 거절한다. 전송 재시도마다 전달 시각과 서명을 새로 만들고 이벤트 본문·ID는 유지한다. 순서가 바뀐 알림은 revision과 현재 결제 조회로 판정한다.

외부 callback 주소를 사용자에게 받지 않는다. 동일 호스트 앱과 결제 프로세스가 정해진 내부 주소로만 통신하고, 키 회전·재시작 후 미전송 outbox 재개도 검증한다.

## 9. 안전성 기준과 결과 대조

| ID | 반드시 유지할 조건 |
|---|---|
| I-01 | 변경 시 원래 주문 ID가 유지된다. 재주문 비교 시나리오와 구분한다. |
| I-02 | 같은 주문의 같은 시점에 제조·수령을 수행할 권한을 가진 매장은 최대 한 곳이다. |
| I-03 | 확정 금액 합계가 마지막 동의 금액과 맞고, 다른 요청키·중복 알림으로 늘지 않는다. |
| I-04 | 거절 후 원래 주문·승인·혜택을 유지한다. 새 승인 보류와 새 자리의 미확정 정리는 숨기지 않는다. |
| I-05 | 주문 수령 완료는 결제 확인과 매장 수령 확인 뒤에만 표시한다. |
| I-06 | 취소 완료는 제조 전 취소와 필요한 승인 해제를 확인한 뒤에만 표시한다. |
| I-07 | 포인트 사용·적립 또는 보류 복원은 같은 주문의 확정 전이에 한 번 반영한다. |
| I-08 | 결제 결과를 확인할 수 없으면 내부 모의 성공으로 대신하지 않는다. |
| I-09 | 다른 방문자의 세계·주문에 결제 장애, 조회, 취소 명령을 적용할 수 없다. |
| I-10 | 프로세스 종료·재시작 뒤에도 같은 파일과 키를 사용해 원래 작업을 계속 확인한다. |

최종 대조 API는 GET이며 주문·매장·결제 서버에서 독립적으로 자료를 읽는다. 주문 이벤트를 세 군데에 복사해서 일치로 판정하지 않는다. 각 원본의 revision과 조회 시각을 포함한다.

서로 다른 저장소는 한 번에 원자적으로 읽히지 않는다. 주문 C0 → 매장 M0 → 결제 P0 → 매장 M1 → 결제 P1 → 주문 C1 순서로 읽고, 관련 주문의 revision이 각각 같으며 미완료 작업이 없을 때만 안정된 대조 결과로 판정한다. 변경 중이면 `PENDING`을 돌려주고 제한된 재조회만 한다. 읽기 실패는 null/미확인으로 남긴다. 대조 API가 복구 명령을 수행하지 않는다.

정상 수령의 대조 식은 `결제 확정 합계 = 최종 동의 청구액`, `불필요한 승인 보류 합계 = 0`, `수령 매장 수 = 1`이다. 다른 방문자의 거래는 합계에 포함하지 않는다. 실제 PG 수수료·카드사 매입·실정산을 검증했다는 표현은 사용하지 않는다.

## 10. 체험 장애와 테스트 전용 장애를 분리한다

공개 체험에서는 해당 방문자 주문의 1회성 효과만 허용한다.

| 공개 시나리오 | 실제로 일어날 가상 처리 | 기대되는 사용자 결과 |
|---|---|---|
| 최초 승인 거절 | 결제 서버가 거절 명령 결과 저장 | 매장 접수·포인트 소모 없음 |
| 승인 후 응답 끊김 | 승인·명령 결과를 commit한 뒤 연결 종료 | 신규 승인 없이 기존 승인 확인 |
| 결제 확정 후 응답 끊김 | 청구 저장 후 응답만 누락 | 같은 청구를 조회, 중복 청구 없음 |
| 동일 알림 2회·오래된 알림 지연 | 저장된 이벤트를 실제 HTTP로 재전달 | 거래와 혜택이 두 번 반영되지 않음 |
| 승인 해제 후 응답 끊김 | 해제 기록 저장 후 응답 누락 | 새 결제 없이 해제 확인 후 취소 완료 |

프로세스 강제 종료·포트 중단·DB 잠금·호스트 재시작은 로컬/CI 전용이다. 공개 화면에 kill, 임의 지연, 파일 경로, SQL, callback URL 입력을 노출하지 않는다. 방문자 한 명이 공유 프로세스를 중단할 수 없게 한다. 공개 faults는 allowlist·버전·세계·횟수로 제한하고 기록한다.

## 11. 기존 주문과 호환성

새 journey에 `protocol_version=2`, `payment_mode=simulator_http_v1`을 저장한다. 배포 전 생성한 journey는 명시적인 구버전으로 유지하고 조용히 마이그레이션하지 않는다. 이미 만든 주문의 payment_mode는 바꿀 수 없다.

새 모드에서 결제 서버가 죽으면 대기·추가 확인으로 남긴다. legacy 내부 승인 이벤트로 fallback하지 않는다. `/api/route/runtime`은 설정 모드와 실제 연결 확인 상태를 분리해서 응답한다. 정적 `payment_transport=http`만으로 준비 완료라고 판단하지 않는다.

기존 `/classic`, `/repair-lab`, 비교 실험의 의미를 보존한다. 과거 비교는 구버전 규칙의 실험임을 명시하며, 새 결제 경로를 비교하지 않았다면 그 성능·안전성 근거로 사용하지 않는다.

UI는 최초 주문이 아직 없는 경우에도 미완료 작업·결제 확인 상태를 먼저 검사한다. `pending_order_id`와 마지막 확인 상태를 보여주고 시작 버튼을 잠근다. 서버에 저장된 참조를 복원하지 못했을 때 localStorage를 지우고 새 주문을 만드는 행동을 하지 않는다.

| PG 통신 | `demo/route/payments/http_server.py`, `http_client.py` | 인증, 크기/시간 제한, 응답 결합 검증 |

| 주문 조정 | `durable_operations.py`, 신규 `payment_steps.py` | 프로토콜 분기와 단계별 복구, 외부 I/O 잠금 분리 |
| 순수 계획·결과 반영 | `store.py`와 필요 시 `command_plan.py` | 견적/혜택 검증과 확인된 결제 증거 반영의 분리 |
| 결과 대조 | 신규 `reconciliation.py` | 독립 조회, revision 확인, 일치/미확인 판정 |
| UI | `guide-flow.js`, 가맹점/결제 패널 자산 | 단계 우선순위, 단말 상태, 쉬운 결과 설명 |
| API 계약 | `api.py`, `response_models.py`, OpenAPI·이벤트 계약 | 입력·오류·payment_mode·증거 응답 명세 |
| 검증·문서 | 테스트, 실제 HTTP/브라우저 스크립트, CI, README | 구/신 경로 회귀와 실행 근거·새 녹화 |

순수 후보 계획을 만드는 단계에서 새 결제 서버의 승인·확정 이벤트를 미리 성공으로 만들지 않는다. 견적과 혜택의 계획은 먼저 검증하되 금융 증거는 확인된 PG 거래 ID를 붙여 최종 반영한다. 기존 이벤트를 삭제하거나 이름만 바꾸어 외부 연동으로 꾸미지 않는다. 최종 반영은 현재 주문 버전·작업 세대를 대조하며, 후보 생성 이후 들어온 inbox 기록이나 복구 관측을 오래된 후보 JSON으로 덮어쓰지 않는다.

## 13. 완료 판정용 테스트 목록 — 아직 미실행

모든 항목은 구현 후 실행해야 할 인수 조건이다. 아래 30개 항목을 기존 테스트 개수나 통과 결과에 더하지 않는다.

| 번호 | 검증 | 통과 기준 |
|---|---|---|
| T-01 | 정상 최초 승인·매장 접수 | 각각의 DB에 대응 기록, 확정 주문 하나 |
| T-02 | 최초 승인 거절 | 매장 부작용·혜택 소모 없음 |
| T-03 | 승인 저장 후 응답 유실 | 같은 승인 ID로 확인, 효과 중복 없음 |
| T-04 | 매장 거절 뒤 승인 정리 | 활성 승인 보류 0, 확정 주문 없음 |
| T-05 | 변경 시 새 승인 거절·한도 부족 | 원래 주문·승인 유지, 새 자리 정리 |
| T-06 | 2,800원→3,200원 변경 | 새 승인·이전 해제 이력, 최종 청구 3,200원 |
| T-07 | 금액 동일·금액 감소 변경 | 명시된 정책대로 처리, 과다 청구 없음 |
| T-08 | 결정 전 기한·늦은 승인 응답 | 늦은 승인 정리 또는 미확인 표시, 완료로 위장하지 않음 |
| T-09 | COMMIT 뒤 프로세스 종료 | 원래 매장 부활 없이 저장된 변경 진행 |
| T-10 | 승인 해제 저장 후 응답 유실 | 중복 해제 효과·중복 혜택 복원 없음 |
| T-11 | 결제 확정 저장 후 응답 유실 | 확정 거래 추가 없음, 조회로 확인 |
| T-12 | 결제 확인 후 매장 수령 응답 유실 | 같은 청구·같은 수령으로 계속 확인 |
| T-13 | 수령 요청 24개 동시 전송 | 한 번 청구·한 번 수령·한 번 적립 |
| T-14 | 동일 키로 다른 금액/주문 | 409, 원장 변화 없음 |
| T-15 | 다른 키로 같은 승인 재확정 | 승인 상태로 중복 금융 효과 차단 |
| T-16 | 이전 승인·이전 세대의 늦은 명령 | 최신 결제/주문으로 반영되지 않음 |
| T-17 | 동일 알림 중복·역순 | inbox 중복 차단, 상태가 과거로 돌아가지 않음 |
| T-18 | 변조 서명·본문 충돌·다른 세계 | 거절, 해당 주문과 다른 주문 모두 불변 |
| T-19 | 페이지 닫기·복구·새로고침 | 서버 복구 독립 실행, 주문 재생성 없음 |
| T-20 | PG/조정 서버 각각 commit 직후 강제 종료 | 파일 보존 재시작 후 동일 키로 재개 |
| T-21 | PG 장기 중단·재시도 8회 소진 | REVIEW_REQUIRED, 가짜 결제 성공 없음 |
| T-22 | PG 미응답 동안 다른 방문자 주문 | 전역 DB 잠금으로 불필요하게 막히지 않음 |
| T-23 | 결제/매장 원본 읽기 실패 | 결과 대조는 미확인, 0건·일치로 대체하지 않음 |
| T-24 | 원장 불일치·조회 도중 revision 변경 | 불일치 또는 진행 중으로 정확히 분류 |
| T-25 | 구버전 활성 주문과 신버전 공존 | payment_mode 고정, 조용한 변환/fallback 없음 |
| T-26 | 0원 주문·잘못된 금액 타입 | NO_CHARGE 명시 또는 입력 거절, PG 과다 요청 없음 |
| T-27 | 고객·원래 매장·새 매장 탭 동시 조작 | 버전·제조 권한 규칙 유지 |
| T-28 | 최초 승인 대기 중 order 없음 | “결제 확인 중” 우선, 신규 주문 유도 없음 |
| T-29 | 데스크톱·모바일·키보드 | 주 흐름과 동의/복구/결과를 실제 클릭·입력으로 완료 |
| T-30 | 계약·README·영상·배포 SHA | 실제 실행 모드와 일치, 로컬/CI/공개 근거 구분 |

각 의미 단위에 실패하는 회귀 테스트를 먼저 만들고 수정 전 실패·수정 후 성공을 확인한다. 금융 부작용 뒤 응답 누락은 테스트가 응답 JSON을 조작하는 대신 가상 서버의 실제 commit 후 연결 종료로 만든다. 브라우저 검사는 성공 버튼을 강제 클릭하거나 서버 상태를 직접 수정하지 않는다.

전체 통합 묶음은 최소 3회, 데스크톱·모바일 핵심 시나리오는 각각 최소 3회 실행한다. 고정된 정상 결과와 거절·추가 확인 반례를 모두 남긴다. 반복 실행 횟수를 독립 사용자 수나 상용 성능 근거로 바꾸지 않는다. 기존 테스트의 기대값을 새 결제 이력에 맞춰 바꿀 경우 의미 변화와 새 독립 원장 단언을 함께 기록한다.

코드·API·계약·기존 회귀·실제 HTTP·프로세스 재시작·브라우저·증거 대조·새 촬영·같은 SHA의 공개 배포를 각각 확인한다. 일부가 남으면 그 항목을 미완료로 보고한다. 아직 실행하지 않은 검증을 과거 376개 테스트나 공개 36회 검사로 대신하지 않는다.

## 14. 단계별 산출물과 배포 경계

첫 산출물은 이 설계 문서다. 다음 구현은 가상 PG의 로컬 상태 전이/실제 HTTP → 영속 결제 단계와 복구 → 기존 매장 화면과 증거 대조 → 회귀/촬영/배포 검증 순으로 분리한다. 이는 작업 순서의 의존관계이며 수행 완료 목록이 아니다.

공개 기본 경로를 신버전으로 바꾸기 전 별도 개발 브랜치에서 전체를 검증한다. 기존 사용자 흐름을 유지하고 새 경로는 정상 결과·실패 결과를 모두 보여줄 수 있어야 한다. 신규 유료 Render 인스턴스나 외부 PG 계정을 만들지 않고 현재 호스트에서 실행 가능한 범위를 먼저 측정한다. 리소스가 부족하면 서비스 구성을 몰래 변경하지 않고 그 한계를 보고한다.

README의 기존 41초 영상을 신기능 영상이라고 부르지 않는다. 새 녹화에는 실행 모드·정확한 커밋·주문/거래 ID·실패 장면·최종 원장 결과를 포함한다. CI 녹화와 공개 녹화를 구분하고, 공개 테스트는 실제 `/health.release_commit` 및 결제 프로세스 준비 상태를 확인한 뒤 수행한다.

이 문서를 저장하는 것만으로 현재 `main`, 공개 앱, 데이터베이스, 결제 동작을 변경하지 않는다.
