# 멀티 호스트 실행·외부 복구 게이트 (`ha_postgres_v1`)

설계: [HA·DB 유실 복구 설계안](superpowers/specs/2026-10-02-ha-disaster-recovery-design.md) · 계획: [Task 5](superpowers/plans/2026-10-02-ha-dr-implementation.md) · 진행 기록: [ha-task5-progress.md](ha-task5-progress.md)

이 문서는 여러 호스트에서 주문·가맹점·가상 결제를 실행하는 구성과, 외부 백업에서 복원한 뒤 다시 운영하는 절차를 설명한다. 기존 공개 Render 서비스와 `main`은 바꾸지 않았다. 유료 자원도 만들지 않았다.

## 1. 현재 상태

| 구분 | 상태 | 근거 |
|---|---|---|
| 구현 완료 | 실행·접속·인증 구성, 인벤토리 승인 검증, Patroni·etcd·진입점·systemd 렌더링, 백업 운영(WAL 전송·보존 계획·경보), 운영 세대·키 교체, 복원 부트스트랩 | 이 브랜치의 커밋 |
| 개발 검증 완료 | 한 컴퓨터의 Docker 컨테이너 3개를 "호스트"로 둔 리허설에서 HA-01~06, WAL 보관, 세대 차단, 전체 클러스터 유실 후 외부 저장소 복원과 API·브라우저 확인 | [진행 기록](ha-task5-progress.md)의 실행 결과 |
| 실제 멀티 호스트 검증 | **부분 완료(2026-10-03).** Oracle Osaka의 서버 4대(범위 `oracle_single_ad_fault_domains`)에서 WAL 보관, HA-01~10(04~10은 3회), DR-01~08(3회) 통과. DR-04 경보 판정은 1회 통과. 실제 공개 DNS 진입점은 안 함 | [최종 보고서](ha-task5-final-report.md) |
| 공개 배포 | **미실행.** 공개 주소는 기존 SQLite 단일 호스트 데모 그대로 | — |

한 컴퓨터 리허설은 구성이 실제로 기동하고 장애 전환·복원 절차가 동작한다는 개발 증거다. 서로 다른 장애 영역의 HA 증거가 아니며, 측정한 초 단위 시간은 운영 RTO/RPO가 아니다.

## 2. 실행 모드와 인증

`PICKUP_ROUTE_BACKEND=ha_postgres_v1`일 때만 아래 규칙을 쓴다. 기존 `postgresql_development`(loopback HTTP)와 SQLite 모드는 그대로다.

### 역할 간 통신 (`demo/route/ha/transport.py`)

- 모든 내부 주소는 HTTPS, 허용 호스트 목록, 명시 포트를 거친다. 환경 프록시와 리다이렉트는 따르지 않는다.
- 서버 신원은 사설 CA와 호스트명으로 확인한다.
- 인증서 SAN의 `urn:pickup-pact:role:<order|merchant|payment>`로 역할을 확인한다.
  - 수신기는 클라이언트 인증서를 요구한다. 가맹점·가상 PG는 `order`만, 결제 알림 수신기는 `payment`만 받는다.
  - 클라이언트는 TLS 직후 서버 역할을 확인한다. 역할이 다르면 요청 바이트와 토큰을 보내기 전에 연결을 끊는다.
- TLS는 인가를 대신하지 않는다.
  - 역할별 Bearer 토큰과 알림 HMAC을 그대로 검사한다.
  - 세 값은 서로 달라야 하고 32자 이상이다.
- 가맹점·결제 origin은 역할마다 최소 두 개, 최대 세 개다. 결제는 알림 수신기 최대 세 곳에 순서대로 전달한다.
- 불명확한 쓰기는 새 키로 재시도하지 않는다. 저장된 작업이 원래 키로 결과를 다시 조회한다.

### 데이터베이스 접속 (`dsn.py`, `privileges.py`, `migrate.py`)

- 서비스는 Patroni 구성원 목록 전체를 담은 libpq DSN으로 쓰기 리더에만 접속한다(`target_session_attrs=read-write`). 단일 프록시나 한 호스트 주소에 의존하지 않는다.
- `sslmode=verify-full`과 명시 CA가 필요하다.
  - DSN에 비밀번호를 넣을 수 없다. 0600 passfile이나 클라이언트 인증서만 받는다.
  - `postgres`·`replicator`·`rewind_user`, `options`·`service`·`hostaddr`는 거부한다.
- 데이터 소유자(주문·가맹점·가상 PG)마다 소유자 사용자와 런타임 사용자를 둔다.
  - 런타임 사용자는 DDL을 실행하지 않고, 검토한 테이블 권한만 받는다.
  - 결제 거래, 결제 명령, 매장 영수증, 요청 기록, 알림 수신 기록은 추가만 할 수 있다.
  - 서비스는 기동할 때 다음 중 하나라도 있으면 시작하지 않는다: 관리 속성, 스키마 생성 권한, 다른 역할 DB 접속 권한, 계약과 다른 테이블 권한.
- 스키마는 소유자가 `python -m demo.route.ha.migrate apply --role <역할> --runtime-user pact_<역할>_runtime`으로 적용한다. 계약에 없는 테이블이 생기면 멈춘다.

### 운영 세대

- 각 DB에 운영 세대 1행이 있다.
  - 복원 후 소유자가 `migrate bump-generation --expected N --reason <복원 ID>`로 compare-and-set 방식으로 올린다.
  - 같은 사유로 다시 실행해도 결과가 같고, 다른 사유가 끼어들면 거부한다.
- 이전 세대로 설정된 프로세스는 다음과 같이 막힌다.
  - 연결을 꺼낼 때마다 세대를 확인하므로 새 세대 DB에 쓰지 못한다.
  - 내부 HTTP와 알림의 `X-Pickup-Generation`이 다르면 503을 받는다. 거절(decline)이 아니므로 원래 작업키는 보류 상태로 남는다.
- 주문·승인·청구의 기존 멱등 키는 바꾸지 않는다.

## 3. 배포 인벤토리와 승인 게이트

`infra/ha/inventory.example.yaml`을 복사해 채운다. `python scripts/ha_inventory.py validate <파일> --stage <단계>`는 모든 문제를 한 번에 보고한다.

| 단계 | 확인 |
|---|---|
| `review` | 서로 다른 물리 호스트·장애 영역 3곳의 PostgreSQL·etcd 홀수 정족수, strict 동기 복제(대기 노드 1개 이상), watchdog `required`, 역할별 두 호스트, 두 장애 영역의 진입점, 사설 주소와 클라이언트 대역, digest 고정 이미지, DB 장애 영역 밖의 HTTPS 외부 저장소, 추가 전용 작성자 자격, DB 호스트 밖의 보존 관리자 자격·암호화 키·복원 영수증, 백업 주기·보존·WAL 지연·용량·경보 기준 |
| `deploy` | 위 조건 + `independent_hosts`, 승인자, 승인일(미래 불가), 월 비용 상한, 유료 자원 여부(관리형 로드밸런서는 유료), 자리표시자 없음 |
| `destructive` | 위 조건 + `ha-rehearsal-<hex>` 시험 ID, 인벤토리 안의 파괴 대상 호스트, 운영 주소 목록과 겹치지 않음 |

`python scripts/ha_inventory.py render <파일> --out <디렉터리>`는 빈 디렉터리에 설정만 만든다. 호스트에 접속하거나 자원을 만들지 않는다. 비밀번호·토큰·개인키는 넣지 않고 경로로만 참조한다.

- `hosts/<호스트>/patroni.yml`: `synchronous_mode`·`synchronous_mode_strict`, `failsafe_mode: false`, watchdog `required`, REST API 클라이언트 인증서 필수, etcd3 HTTPS, `hostssl`+SCRAM만 허용하는 `pg_hba`, WAL 스풀 `archive_command`
- `hosts/<호스트>/etcd.env`: 클라이언트·피어 양쪽 인증서 인증
- `hosts/<호스트>/pickup-<역할>.env`: 역할별 비밀이 아닌 설정. 같은 호스트의 역할을 먼저 쓰고 나머지를 장애 전환 순서로 둔다
- `hosts/<진입점>/haproxy.cfg`(+`keepalived.conf`): `/ready` 상태 확인, 앱 구간 TLS·클라이언트 인증서, 요청이 서버에 닿지 않았을 때만 재시도(응답 유실 요청은 다시 보내지 않음)
- `cluster/bootstrap.sql`: 역할별 DB·사용자, `PUBLIC` 접속 회수. 비밀번호는 `python -m demo.route.ha.scram`이 만든 SCRAM 검증값으로 따로 설정한다
- `cluster/backup-policy.json`, `cluster/entry-dns.json`, `MANIFEST.json`(인벤토리·파일 해시, 통과 단계)
- systemd 단위는 `infra/ha/systemd/`에 있다. 비밀은 `/etc/pickup-pact/secrets/*.env`(0600, 운영자 공급)에서만 읽는다.

## 4. 외부 백업 운영

- **WAL 보관**
  - `infra/ha/pickup-wal-archive`가 WAL을 별도 디스크의 스풀로 복사한다. 같은 이름이 다른 내용으로 이미 있으면 실패해 PostgreSQL이 세그먼트를 보존하고 다시 시도한다.
  - `backup_ops.ship_wal`은 스풀 묶음을 Restic 스냅샷 하나로 올린다. 스냅샷 목록의 이름·크기를 확인한 뒤에만 스풀에서 지운다. 실패하면 하나도 지우지 않고 상태 파일에 기록한다.
  - `.partial`·`.backup`·`.history` 파일도 함께 보관한다.
- **자격 분리**
  - DB 호스트는 append-only REST 작성자 자격만 가진다. 이 자격으로는 스냅샷을 지울 수 없다.
  - `forget`/`prune`은 DB 호스트 밖 보존 관리자 자격으로만 실행한다.
  - `backup_ops plan`은 지울 스냅샷 ID를 명시한 명령만 출력하고 직접 실행하지 않는다.
- **보존**
  - 검증된 최신 기본 백업 N개를 남긴다.
  - WAL 스냅샷은 그 안의 모든 세그먼트가 남길 백업에 필요한 가장 이른 위치보다 앞설 때만 지울 수 있다.
  - 다음 경우에는 아무것도 지우지 않는다: WAL 구멍, history 파일 없는 타임라인, 검증 백업 부족.
- **감시**: `python -m demo.route.ha.backup_ops assess --policy cluster/backup-policy.json --status <수집 상태>`.
  - 경보 종류: 기본 백업 없음·노후·미검증, `archive_command` 실패, 스풀 지연·용량, 업로드 실패, 저장소 용량, 보존 차단.
  - `measured_exposure_s`는 마지막으로 외부에 확인된 WAL 이후 경과 시간이다. 목표 RPO가 아니라 현재 측정값이다.
- **키·영수증**: 암호화 키와 복원 영수증(저장소 ID·전체 스냅샷 ID·봉인 해시·클러스터 ID·목표 WAL 위치)은 DB 호스트와 같은 유실 경로에만 두지 않는다. 인벤토리 `key_escrow`·`receipt_locations` 검증이 이를 강제한다.

## 5. 복원 후 재개 절차

1. 이전 클러스터의 쓰기를 차단한다(호스트 격리 또는 서비스 중지). 복원 대상은 새 볼륨·새 etcd다.
2. 별도로 보관한 영수증과 봉인 해시로 고정 스냅샷을 내려받는다(`ResticArchive.restore`). `latest`나 짧은 ID는 쓰지 않는다.
3. 인벤토리에 `restore`(새 리더, 기본 백업·WAL 경로, 목표 이름)와 `operating.generation: N+1`을 넣고 렌더링한다.
   - 지정한 리더만 `pickup-restore-bootstrap`으로 데이터 디렉터리를 만든다(`pg_verifybackup` 후 복사, 비어 있지 않으면 거부).
   - 목표 지점에서 승격한다. 나머지 구성원은 새 리더를 복제한다.
4. 소유자·런타임 DB 비밀번호와 역할 토큰·알림 비밀을 새로 발급하고, 운영 세대를 올린다.
5. 새 세대 설정으로 서비스를 시작한다. 이전 토큰·이전 세대 요청은 거부된다.
6. 다음을 대조한 뒤에만 진입점을 연다.
   - 완료 주문·진행 중 주문·결제 원장·매장 영수증·혜택
   - 목표 이후 기록이 없는지(유실 구간으로 보고)
7. 진행 중이던 청구는 원래 작업키로 결과를 조회해 마친다. 새 키로 다시 청구하지 않는다.

## 6. 독립 호스트 시험 계획 (승인 후)

각 시나리오는 독립 초기 상태에서 3회 반복한다. 실패한 회차도 지우지 않고 보존한다. 결과에는 다음을 남긴다.
- 코드 SHA, 인벤토리 해시, 호스트·장애 영역 배치, 복제 상태
- 백업 manifest·영수증, 복구 전후 원장, 측정 시각

| ID | 실제 호스트에서의 실행 | 통과 기준 |
|---|---|---|
| HA-01 | 같은 요청을 서로 다른 호스트의 앱으로 | 같은 주문·결과, 다른 내용의 같은 키는 409 |
| HA-02 | 청구 응답 유실 후 그 앱 호스트 전원 차단 | 다른 호스트 작업자가 원래 키로 마침, 청구 1건 |
| HA-03 | 가맹점 또는 가상 PG 호스트 전원 차단 | 다른 호스트로 재확인, 로컬 모의 성공 없음 |
| HA-04 | 주 DB 호스트 전원 차단 | 동기 대기 노드 승격, 응답한 쓰기 보존, 불명확 요청 별도 집계 |
| HA-05 | 대기 DB 호스트 1대, 이어서 2대 중단 | 남은 노드로 동기 회복, 대기 노드가 없으면 쓰기 응답 0건, 조건 자동 완화 없음 |
| HA-06 | 리더 호스트의 클러스터 망 분리 후 복귀 | 쓰기 리더 동시 2개 없음, 옛 리더 쓰기 차단, pg_rewind 후 재합류 |
| HA-07 | 복구 작업자 동시 실행·임대 만료 | 같은 외부 키, 늦은 응답 거부, 다른 주문 진행 |
| HA-08 | 한도·중복 청구 동시 경합 | 한도 초과 승인·두 번째 확정 차단 |
| HA-09 | 다중 탭·중복·지연 알림 | 주문·제조·수령·금융·혜택 불변조건 유지 |
| HA-10 | 진입점 호스트 1대 중단·복귀 | 공개 주소가 남은 진입점으로 계속 응답 |
| DR-01 | 클러스터 데이터·WAL 스풀·etcd 전체 제거 | 외부 저장소만으로 새 클러스터 복원, 복제본 미사용 명시 |
| DR-02 | 오삭제 직전 지점 복원 | 선택 지점과 복원 거래 집합 일치, 이후 기록 없음 |
| DR-03 | WAL 누락·파일 변조·업로드 미완료 | 유효 백업으로 승인하지 않음 |
| DR-04 | 저장소 중단·용량 한계 | 경보, 불완전 백업 성공 처리 없음, 스풀 보존 |
| DR-05 | 매장 변경·청구 진행 중 복원 | 원래 키로 재개, 재청구 없음 |
| DR-06 | 복원 전 요청·알림 재도착 | 이전 세대·이전 토큰 거부, 기존 거래 조회 가능 |
| DR-07 | 키·영수증을 DB 호스트 밖에서 복구 | 승인 경로로 복원, 비밀이 증거에 없음 |
| DR-08 | 운영 주소·비시험 볼륨 지정 | 파괴·복원 명령 거부 |

다음 기준으로 측정한다.
- RTO: 장애 판정부터 검증 완료와 진입점 재개까지의 실제 관측 시간
- RPO: 보존·복원된 마지막 기록과 장애 시각의 차이
- 개발 리허설 시간은 이 값으로 쓰지 않는다.

## 7. 승인 요청 — 실제 독립 호스트 시험에 필요한 것

아래가 정해지기 전에는 서버·저장소를 만들지 않고 파괴 시험도 하지 않는다.

1. **호스트 3대**: 서로 다른 장애 영역(가용 영역 또는 물리 서버)의 Linux VM. 리허설 규모 기준 2 vCPU·4 GiB·디스크 40 GiB 이상이며, watchdog 장치(`/dev/watchdog`, 예: softdog 또는 하이퍼바이저 watchdog)를 쓸 수 있어야 한다.
2. **외부 백업 저장소 1곳**: 세 장애 영역과 다른 곳의 HTTPS append-only REST 저장소 또는 승인된 객체 저장소. 작성자·보존 관리자 자격을 분리할 수 있어야 한다.
3. **진입점 방식**: 두 호스트 DNS 다중 A 레코드(추가 비용 없음), keepalived VIP(같은 L2망 필요), 관리형 로드밸런서(유료) 중 하나.
4. **비용**: 제공업체·지역·월 비용 상한(원). 실제 단가는 승인자가 제공업체 가격표로 확정한다. 이 문서는 금액을 추정해 승인으로 쓰지 않는다.
5. **접근·비밀**: 호스트 접속 방식, 사설 CA·인증서 발급 위치, 비밀 저장소(키 보관 위치 1곳 이상은 DB 호스트·백업 저장소 밖).
6. **파괴 범위**: 시험 기간, `ha-rehearsal-<hex>` ID, 파괴해도 되는 호스트 목록, 절대 건드리면 안 되는 운영 주소 목록(기존 Render 공개 서비스 포함).
7. **승인자 이름과 날짜**: 인벤토리 `approval`에 기록하고 `deploy`·`destructive` 단계를 통과해야 시작한다.

## 8. 남은 제약

- 한 컴퓨터 리허설에서는 watchdog를 끈다(`single_host_rehearsal`에서만 허용). 실제 리더 차단은 독립 호스트 시험에서 확인해야 한다.
- HA-10(진입점)은 실서버에서 HAProxy 두 대로 시험했다(자체 서명 인증서, 공개 DNS 없음). 로컬 리허설에서는 하지 않았다. 리허설의 브라우저 확인은 복원 클러스터에 mTLS로 연결한 loopback 앱으로 했으며, 공개 TLS 진입점 경로가 아니다.
- 리허설의 외부 저장소는 같은 컴퓨터의 별도 프로세스다. 다른 장애 영역에 있다는 증거가 아니다.
- Patroni 자체 계정(`postgres`·`replicator`·`rewind_user`)의 비밀번호 교체는 운영자 절차로 남겨 두었다. 리허설은 금고에 보관한 값을 다시 쓴다.
