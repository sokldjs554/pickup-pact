# 쿠폰·포인트와 매장 이동의 효과 비교

## 고객이 직접 하는 일
첫 화면에서 쿠폰과 사용할 포인트를 선택한다. 각 매장 카드에는 메뉴금액, 쿠폰 할인, 사용 포인트, 최종 모의 결제액이 나온다. `혜택 적용 후 결제 예산`은 현금 결제 예정액의 상한이다.

기본 라떼에서 전 매장 500원 쿠폰과 1,000P를 선택하면 웨이브는 4,300 − 500 − 1,000 = **2,800원**이다. 주문 시 혜택을 보류하고, 수령할 때 한 번 사용 확정한다. 순수 모의 결제 2,800원의 1%인 28P가 적립되므로, 체험 지갑은 2,000 − 1,000 + 28 = **1,028P**가 된다.

웨이브 전용 1,000원 쿠폰을 쓰면 웨이브 주문은 2,300원이다. 오트로 이동하는 견적에서는 해당 쿠폰을 사용할 수 없어 3,700원이다. 이동 확인창에 **쿠폰 할인 1,000원 상실과 실제 결제 차액 +1,400원**을 표시하고 사용자가 동의한 견적만 처리한다. 예산이 3,000원이면 이동을 거절한다. 취소 후 재주문을 가장해 차액을 숨기지 않는다.

## 적용 정책 — 이 데모의 명시적인 규칙
| 항목 | 규칙 |
|---|---|
| 지갑 | 일정마다 2,000P를 갖는 독립된 모의 지갑. 계정 간/주문 간 공유 지갑 아님 |
| 전 매장 정액 | `welcome500`: 메뉴 3,000원 이상 500원, 가상 시각 11:40까지 |
| 매장 전용 정액 | `wave1000`: 웨이브에서 메뉴 4,000원 이상 1,000원, 09:40까지 |
| 정률 | `morning10`: 메뉴 3,000원 이상 10%, 최대 800원, 09:10까지 |
| 할인 순서 | 메뉴금액 → 쿠폰 1장 → 포인트 → 현금 결제 예정액 |
| 포인트 | 정수 0~2,000. 잔액 초과 입력 거절, 할인 후 잔액보다 많이 사용할 수 없음 |
| 보류와 확정 | 주문 때 혜택 보류, 수령 때 사용 확정·순결제액의 1% 적립, 반복 수령은 중복 차감/적립 없음 |
| 제조 전 취소 | 쿠폰·포인트 보류를 해제. 반복 취소로 잔액이 불어나지 않음 |
| 만료 | 새로 보류할 때 확인. 기존 주문에 보류된 혜택은 인정하지만 취소로 만료일을 연장하지 않음 |
| 매장 이동 | 원래 보류를 새 견적으로 원자 교체. 제조 시작 후 이동/자동 취소 금지 |

쿠폰 최소금액은 포인트 차감 이전의 메뉴금액으로 판단한다. 유효하지 않은 쿠폰을 선택하면 할인 0원과 사유를 보여준다. 혜택 미선택은 기존 가격과 같다. 기존 저장된 주문에 혜택을 소급 적용하지 않는다.

주문·지갑·혜택 이벤트의 최종 반영은 주문 SQLite DB의 같은 트랜잭션에 묶인다. 신규 주문의 매장 자리와 처리 영수증은 매장별 별도 DB에 저장하며, 사이의 실패는 저장된 작업 단계로 재확인한다. 자세한 순서는 [매장 변경 복구](transfer-recovery.md)를 따른다. 오류를 주입한 커밋 직전 실패에서 변경 전 상태가 그대로 남는지 검증한다. 실제 PG/제휴사 쿠폰/가맹점 시스템을 연결했다는 뜻은 아니다.

## 비교는 두 종류이며 의미가 다르다
### 현재 주문 비교
현재 주문을 유지할 때와 각 대안의 목적지 도착 예상, 결제액 차이, 쿠폰 할인 상실을 **동일 상태 버전**에서 계산한다. 새 견적을 승인할 때 서버가 상태와 가격을 재검증한다. 이전 도착 예상과 변경 후 예상은 이동 이벤트에 보존한다. 예상값이지 실제 도착 기록은 아니다.

### 동일 조건 합성 정책 실험
`기존 매장 유지`와 `위험할 때 조건에 맞는 매장으로 제조 전 이동`을 같은 초기 주문·관찰 가능한 혼잡·예산·쿠폰·포인트·추가 지연으로 비교한다. 실제 패스오더 추천 알고리즘이나 국내 다른 지원자의 코드를 대신 실행하지 않는다.

6개 상황: 혼잡 없음, 주문 매장만 혼잡, 대체 매장도 혼잡, 이미 제조 시작, 쿠폰 상실·예산 제한, 선택 후 예상 밖 지연. 사례별 미래 지연은 매장마다 고정되어 두 정책에 동일하게 적용하되, **선택 함수에는 전달하지 않는다**. 일반 상황 0~3분, 불확실 상황 0~12분의 추가 지연이다. 매장별 독립 오차와 동일 비중의 상황 분포는 설명용 모델 가정이며 관측 자료에 적합한 확률모형이 아니다.

시드별 모든 사례를 분모에 포함한다. 처음부터 주문할 수 없는 경우, 양쪽이 실패하는 경우, 이동 후 악화된 경우를 삭제하지 않는다. 개선/악화는 모형상의 마감 충족 여부가 바뀐 경우이며, 두 정책 모두 충족 또는 미충족이면 동일 결과로 센다. 비용 평균의 분모는 최초 주문 가능 사례 전체이며, 최대 비용 증가도 공개한다.

경로와 견적은 제품과 같은 `planner.py`/`benefits.py`를 사용한다. 별도 시험은 실험 정책이 선택한 견적이 실제 `JourneyStore.command()`의 이동 트랜잭션에서도 같은 가격·도착 예상으로 처리되는지 확인한다. 실험 자체의 점수는 모델 추정 시간에 숨겨진 지연을 더한 값이며, 실물 주문의 배송/수령 성공률이 아니다.

### 재현
```bash
PYTHONPATH=.:services/reconciler python -m pytest -q tests/route
python scripts/route_outcomes.py --seeds 7 19 31 --cases 120 --output verification/route-outcomes
python scripts/verify_benefits_browser.py --base-url http://127.0.0.1:10000 --repeat 3
```
Windows PowerShell에서는 `$env:PYTHONPATH=".;services/reconciler"`를 설정한다. Chromium은 Playwright 설치가 필요하다. CI가 각 시드의 전체 JSON/CSV를 3회 생성해 동일성을 확인하고, 새로운 혜택 흐름을 desktop/mobile에서 각각 3회 검증한다. 공개 실행은 배포 커밋 일치 확인을 별도로 수행한다.

API: `/api/route/journeys/{id}/comparison`, `POST /api/route/experiments` (`seed`: 0~1,000,000, `cases`: 6~200). 입력 상한과 제한된 결과 캐시가 있다. 첫 화면에서는 시드 7/19/31, 각 120건 비교와 원본 JSON 저장을 제공한다. OpenAPI 스냅샷: `contracts/route-benefits.openapi.json`.

## 이번 모델로 입증하지 않는 것
실제 지도/GPS 정확도, 실제 가맹점의 제조 처리량과 공유 용량, 운영용 계정·권한·공유 포인트 지갑, 제휴사 쿠폰 정산, 실제 PG 환불, 실매출/전환율/시장 우위를 입증하지 않는다. `queue_until`은 합성 혼잡을 나타낸다. 기존 Java/Kafka/PostgreSQL 검증은 별도이며 새 SQLite 제품이 그 분산 서비스들을 호출하는 것은 아니다.

새로운 6가지 상황의 유지/취소 후 재주문/동일 주문 변경 비교는 위 120건 정책 실험과 별개다. [비교의 기준과 한계](transfer-recovery.md)를 확인한다.
