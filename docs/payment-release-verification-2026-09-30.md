## 제품에서 바뀐 점

주문 조정 서버, 가맹점 HTTP 프로세스, 독립 SQLite를 가진 가상 결제 HTTP 프로세스를 연결했다. 승인·청구·승인 해제의 저장 후 응답 유실은 서버에서 실제 연결을 끊어 재현한다. 복구는 저장된 작업 키로 처리 기록을 확인하며, JSON 응답을 성공으로 바꾸는 방식이 아니다.

금액 변경에 동의하면 새 승인 확보, 매장 변경, 기존 승인 해제 순서로 진행한다. 승인 보류 두 건과 최종 중복 청구를 구분한다. 실제 카드번호·비밀키·상용 PG 결제창은 사용하지 않는다. 두 매장의 단말은 실제 원본 저장소에서 읽은 상태와 최근 처리 기록을 보여준다. 기존 주문의 제조 동작은 주문 조정 API를 거쳐 충돌 규칙을 유지한다.

마지막 결과는 주문·가맹점·가상 PG를 각각 읽어 비교한다. 독립 원장에 접근하지 못하면 0건이나 정상으로 바꾸지 않는다. 두 번 읽는 사이에 내용과 변경 순번이 달라지면 확인 중으로 표시한다. 이는 관측한 안정 구간이며 분산 원자적 스냅샷이 아니다.

## 실패를 먼저 재현하고 고친 항목

원본 대조의 최초 구현은 확정 주문이 없는 승인 거절 상태에서 PG 잔액만 보고 모든 검사를 일치로 표시할 수 있었다. 남은 가맹점 예약·혜택 보류와 수령 후 잘못된 쿠폰·잔액을 주입한 네 가지 회귀가 먼저 실패했다. 각 원본을 별도 검사하도록 고친 뒤 대조 12개가 통과했고 전체 검사에 포함했다.

다른 탭에서 주문을 바꾼 뒤 대조 새로 읽기를 누르면, 이전 ‘일치’ 표시를 지운 뒤 최신 주문 버전을 GET으로 읽도록 수정했다. 원래 코드의 비동기 함수에서 최신/과거/다른 주문 응답을 재현한 세 검사 모두 실패했고, 수정 뒤 세 검사가 통과했다. 이 JS 테스트를 브라우저 검증으로 바꾸어 부르지 않는다. 별도 실제 다중 탭 검사는 관찰 탭을 재로딩하지 않고 원본 확인 버튼으로 상태가 갱신되는지 검사한다.

최초 전체 core 실행 445개에서는 오래된 OpenAPI 스냅샷 하나가 실패했다. 실제 새 API 스키마로 갱신하고 관련 다섯 검사를 통과했으며 최종 전체 반복 검사에서 다시 확인했다.
