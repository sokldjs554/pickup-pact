## 2. 시험 환경

- Oracle Cloud(무료 체험 크레딧, 업그레이드 안 함), Japan Central(Osaka) 단일 가용 영역.
- DB 서버 3대: E5.Flex 1 OCPU·6GB, FD-1/2/3에 하나씩. PostgreSQL 17.11, Patroni 4.0.4(strict 동기, watchdog 필수), etcd 3.5.17(mTLS 3노드), 역할 서비스 5종.
- 백업 서버 1대: E2.1.Micro, FD-1. 이 서버는 DB 서버 한 대와 FD를 공유한다(FD가 3개뿐이어서 승인 예외 `backup_failure_domain`으로 기록).
- 시험 도구는 클러스터 밖인 백업 서버에서 실행하고, 장애는 SSH(`from=10.0.0.20`으로 제한한 임시 키)로 주입했다.
- 한계: 호스트 장애는 전원 차단이 아니라 `sysrq b` 즉시 재부팅(정상 종료·동기화 없음)이다. 장시간 정지는 부팅 후 DB 역할이 올라오지 않게 하는 조건 파일로 모사했다. 망 분리는 서버 방화벽 규칙이다. watchdog는 소프트웨어 `softdog`다. 3회 반복은 매번 새 클러스터가 아니라 같은 클러스터에서 연속 실행했다(DR은 매 회 전체 삭제 후 복원).

### 3.4 동시 경합(HA-07~09, 각 3/3 통과)
두 가지 방식으로 확인했다.
- **실서버 PostgreSQL 17.11(리더 pact-a)에서 불변조건 시험 묶음**: 시험 전용 데이터베이스를 만들어 쓰고 지웠다. HA-07 13개(낡은 소유자의 덮어쓰기 거부, 임대 만료·인수, 작업자 중복 청구 방지, 다른 주문을 막지 않음), HA-08 9개(같은 키 동시 요청 → 영수증 1개, 다른 키로 같은 주문 두 번 확정 불가, 한도 경합), HA-09 11개(다중 인스턴스·중복·지연 알림, 혜택·매장 용량 불변조건)가 각 3/3 통과, 건너뜀 0. 이 시험은 리더 서버 한 대 안에서 도는 동시 경합이다.
- **세 호스트의 앱에 동시에 요청을 보내는 시험**(pact-backup에서 실행):
  - HA-07: 청구 응답이 유실된 주문 6건이 동시에 보류된 상태에서 세 호스트의 복구 작업자가 경합했을 때 주문마다 청구 1건·보류 0(3.3~3.6초에 모두 정리).
  - HA-08: 같은 주문의 확정을 세 호스트에서 서로 다른 키로 동시에 보내면 1건만 효력(나머지 거부), 청구 1건. 같은 키 3개를 동시에 보내면 모두 오류 없이 응답하고 원래 처리는 정확히 한 번이며, 처리가 끝난 뒤 같은 키로 다시 보내면 세 호스트 모두 원래 응답과 같다.
  - HA-09: 같은 주문 상태에서 6개 탭이 서로 다른 키로 같은 전이를 동시에 보내면 1건만 효력(나머지 5건 거부), 이후 끝까지 진행해 청구 1건·포인트 사용 1,000·적립 32.
- 관찰: 같은 키의 요청이 이미 처리 중일 때 도착한 동시 중복 요청은 두 번째 처리를 하지 않고 **처리 중 보기**(주문 `READY`, 결제 처리 `PENDING`, `duplicate: true`)를 돌려준다. 시험의 처음 기대(모든 응답이 동일)는 이 설계된 동작과 달라 첫 실행이 실패했고, 코드(`coordinator.py`의 처리 중 작업 판정)와 순차 재전송 진단(원래 응답과 동일)으로 확인한 뒤 기대를 "동시 중복은 오류 없이 응답하고 효과는 한 번, 완료 뒤 재전송은 원래 응답과 동일"로 고쳤다.

### 3.5 진입점 호스트 중단·복귀(HA-10, 3/3 통과)
pact-a와 pact-b에 HAProxy 진입점(인벤토리가 렌더링한 설정, 앱까지 mTLS)을 설치하고, 시험 도구가 공개 주소(이름 하나에 진입점 두 곳의 주소)를 브라우저처럼 섞어 시도하는 클라이언트로 접속했다. 진입점 한 대를 두 방식으로 멈췄다.

| 방식 | 중단 중 요청(회당) | 실패 | 응답한 진입점 | 최대 지연 | 복귀 |
|---|---|---|---|---|---|
| HAProxy 서비스 중지(pact-a) | 75~77건 | 0 | 남은 진입점만 | 33~228ms | 0.1초 안에 응답, 이후 두 진입점이 함께 서비스 |
| 방화벽으로 443 무응답(pact-b) | 11~25건 | 0 | 남은 진입점(복구 직전에 연결을 기다리던 요청 제외) | 약 3.0초(연결 시간 초과 후 다른 주소로) | 0.1초 안에 응답, 이후 두 진입점이 함께 서비스 |

- 중단 중에 시작한 주문 전체가 공개 주소를 거쳐 끝났고 청구 1건·보류 0이었다.
- **관찰(한계)**: 이미 열려 있던(재사용) 연결은 진입점이 조용히 사라지면 클라이언트의 읽기 시간 초과까지 멈춘다(측정 5초 = 시험의 읽기 시간 초과). 새 요청은 남은 진입점으로 간다. 그래서 판정은 새 연결 기준이며, 이 한계는 헬스체크가 있는 DNS 제공업체나 클라이언트의 짧은 시간 초과·재시도로 줄여야 한다.
- 시험 설계를 세 번 고쳤다. ① 측정 시작을 장애가 실제로 적용된 뒤로 옮김, ② 복구 직전 4초에 연결을 기다리던 요청은 복구 뒤 SYN 재전송으로 연결될 수 있어 "어느 진입점이 응답했나" 판정에서 제외, ③ 재사용 연결 때문에 생긴 실패 1건은 새 연결 기준 판정과 재사용 연결 노출의 별도 측정으로 분리. 서비스 설정은 바꾸지 않았다.

## 4. 실서버에서 처음 드러나 고친 문제 (로컬 리허설에서는 보이지 않았음)

1. **Oracle 네트워크 규칙**: 서브넷의 Security List에 규칙이 없어 서버 간 포트가 차단 → 소유자가 규칙(10.0.0.0/16 TCP)을 추가.
2. **같은 FD에 놓인 DB 서버**: 첫 점검(서버 메타데이터)이 pact-a와 pact-b가 같은 FD임을 잡아 pact-a를 FD-1에 다시 만듦.
3. **재부팅 뒤 `/dev/watchdog` 없음**: Patroni가 시작하지 못해 복귀 실패 → `patroni.service`가 시작 전에 `softdog`를 올리도록 수정.
4. **오래 내려간 대기 노드 복귀 불가**: 새 리더의 WAL이 정리되어 따라잡지 못함 → `wal_keep_size: 2GB` 설정(테스트 포함), 정체된 노드는 `reinit`.
5. **망 분리 때 DB 연결이 오류 없이 멈춤**: DB 풀에 `keepalives*`·`tcp_user_timeout=10000` 추가(테스트 포함).
6. **시험 설계**: 즉시 재부팅한 호스트가 리더 임대 TTL 안에 돌아오면 장애 조치가 일어나지 않음(정상 동작) → 정지 조건 파일로 장시간 정지를 모사. 장애 조치 중 503은 같은 요청 키로 재시도.
7. **복원 시험 도구**: 저장소 인증서 변수가 클라이언트 인증서 경로를 덮어써 첫 DR 실행이 검증 전에 멈춤. 그 실행은 증거로 쓰지 않고 수정 후 같은 범위로 다시 실행.

## 5. 보안·권한 처리
- 비밀값(비밀번호·토큰·저장소 키·CA 개인키)은 저장소·아티팩트·로그에 남기지 않았다. 러너 메모리와 서버의 0600 파일, 백업 서버의 `/dev/shm`에만 있었다.
- CA 개인키는 배포가 끝나면 버려졌다. 인증서는 5일 유효하다.
- 영구 SSH 개인키는 서버에 올리지 않았다. 시험 도구용 임시 키는 `from=10.0.0.20`으로 제한해 시험 동안만 등록했다가 제거했다.
- 파괴 시험은 인벤토리 승인(대상 호스트·기간)을 다시 검사한 뒤에만 실행했고, 운영 주소(`pickup-pact-demo.onrender.com`)는 보호 목록에 있다. 기존 공개 데모·Render 설정·BrewSlot·다른 저장소는 건드리지 않았다.

## 6. 하지 않은 것 (정직한 한계)
- **HA-10의 범위**: 실제 공개 DNS(헬스체크하는 다중 A 레코드)와 공인 인증서 없이, 이름 하나에 진입점 두 곳의 주소를 쓰는 클라이언트와 자체 서명 인증서로 시험했다. 진입점→앱 구간의 mTLS 클라이언트 신원은 CA 개인키가 배포 뒤 폐기되어 etcd-client 잎 인증서를 재사용했다. 렌더링된 HAProxy 설정에 접근 로그 설정이 빠져 있다(`log global` 없음, 설정 검사 경고). 시험 증거는 이 설정으로 얻었다.
- **DR-04의 경보 판정**: 실서버에서는 안 했다(로컬 `verify_ha_backup_ops.py`가 근거).
- HA-07~09의 시험 묶음은 리더 서버 한 대 안에서 도는 동시 경합이고, 세 호스트 동시 요청 시험은 앱 API 수준이다(다른 호스트의 데이터베이스 세션을 직접 경합시키지는 않았다).
- 한 가용 영역·같은 클러스터 연속 3회·소프트웨어 watchdog·즉시 재부팅 모사는 위 2장의 한계 그대로다. Patroni 자체 계정 비밀번호 교체는 운영자 절차로 남아 있다.
