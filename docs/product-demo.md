# Pickup Pact — 일정 중심 커피 주문

## 제품의 핵심
가까운 매장을 고르는 데서 끝나지 않고, 커피를 받아 목적지에 도착할 수 있는 경로를 선택한다. 선택한 매장이 혼잡해지면 제조 전에 동의한 다른 매장으로 같은 주문을 이어간다. 고객·매장·수령·영수증이 하나의 저장된 journey와 order ID를 사용한다.

새 제품은 `/` 또는 `/go`, 이전 주문 화면은 `/classic`, 기존 복구 작업대는 `/repair-lab`이다. 새 제품이 기존 고정 샘플 작업대를 호출하는 구조는 아니다. 복구 작업대와 JVM/Kafka/PostgreSQL topology는 기존 검증 영역으로 보존한다.

## 직접 확인하는 순서
1. 기본 조건: 오피스 타워, 16분 이내, 라떼, 5,500원, 우회 5분.
2. `내 일정에 맞는 커피 찾기`에서 제조 대기와 목적지까지의 이동을 함께 확인한다.
3. 웨이브 로스터스에서 주문한다. 주문 번호를 확인한다.
4. `현재 매장 12분 더 혼잡`을 누른다. 현재 경로의 시간 위험과 대안을 확인한다.
5. 오트 스튜디오 이동을 선택하고 차액을 읽은 뒤 동의한다. 주문 번호는 유지된다.
6. `매장`에서 가상 시계를 진행하고 제조 시작·준비 완료를 실행한다.
7. `내 이동`에서 표시된 수령 코드를 입력하고 커피를 받는다.
8. `영수증`에서 최초 매장, 이동, 차액, 최종 모의 결제 1건을 확인한다.

엄격한 예산·디카페인·오트·우회 조건에서도 같은 방식으로 계산한다. 해가 없으면 불가능한 이유를 보여주며 조건을 몰래 완화하지 않는다. 제조 후 이동, 오래된 quote, 중복 명령과 잘못된 수령 코드를 거절한다.

## 실제 동작 범위
가상 동네의 그래프에 대한 경로 탐색과 합성 제조 대기 계산이다. 실제 GPS, 가맹점 연동, PG 결제나 실물 POS는 아니다. 대안은 가상 현재 시각과 고정 출발지에서 보수적으로 계산한다. 여행 중 위치를 추적하지 않는다. 각 journey의 매장 대기는 독립적이며 여러 고객이 공유하는 실매장 수용량 모델이 아니다.

주문 변경·모의 승인 금액 조정·수령 기록은 단일 SQLite 트랜잭션에 보존된다. 서로 다른 실제 가맹점 DB 사이의 분산 이관이나 실제 카드 승인 변경을 증명하지 않는다. 데모 세션은 추측이 어려운 ID로 구분하지만 운영용 고객·점주 인증 서비스는 아니다. Render 임시 디스크는 재배포 시 초기화될 수 있다.

## 검증 방법
`PYTHONPATH=.:services/reconciler python -m pytest -q tests/route services/reconciler/tests demo/test_demo.py demo/test_repair_integration.py`

`python scripts/verify_route_browser.py --base-url http://127.0.0.1:10000 --repeat 3`

공개 배포 검증은 동일 명령에 공개 base URL과 `--expected-commit <main SHA>`를 사용한다. `route-product` CI는 Python 시험을 3회 반복하고 실제 HTTP Chromium 데스크톱·모바일에서 각각 3회 주문→혼잡→동의 이관→제조→수령→영수증을 실행한다. 소스 ZIP·SHA·시험 로그·결과·화면 캡처를 같은 실행의 artifact로 저장한다. main에서는 정확한 배포 SHA를 기다린 뒤 다시 공개 사이트를 검증한다.

최종 입력 감사에서 비ASCII 수령 코드가 HTTP 500을 일으키는 반례 3개를 재현했다. UTF-8 바이트 비교로 409 거절을 복원하고 주문·금액·이벤트가 바뀌지 않음을 확인했다. 수정 후 로컬 새/기존 Python 시험 196개가 3회 통과했다. 로컬 Flask/JVM/Docker 및 실제 브라우저 결과는 이 수치에 포함하지 않으며 CI에서 따로 검증한다.
