# 공개 반복 검증의 상황 선택 순서 수정

대상 main은 `dfe496d636afd12352b52f00a3744635b8123f9c`, 실패 실행은 `36164292234`, job `108168162628`이다. 내부 Python·HTTP·네 가지 브라우저 시험은 통과했지만 공개 복구 시험 첫 회차에서 PENDING 버튼을 찾지 못했다. 후속 공개 시험은 실행되지 않았으므로 이 실행을 전체 성공으로 계산하지 않는다.

## 확인한 원인

실패 artifact `10877565628`의 원본 영상과 네트워크 기록을 대조했다. 첫 거절 응답은 10.887초에 왔고 화면에 거절이 표시됐다. `cmd()`가 확인된 거절을 표시한 뒤 `run()`의 후속 조회가 10.892~11.994초에 한 번 더 화면을 그렸다. 검사 함수는 화면에 거절이 보이자 다음 조건을 선택하고, 그 뒤에만 busy 해제를 기다렸다. 선택 상자는 버튼과 달리 앞선 명령 중에도 편집할 수 있으므로 이 갱신에 의해 선택값이 저장된 'none'으로 돌아갈 수 있었다.

원본 영상 12.6초 프레임에는 '문제 없이 변경' 선택과 '문제 없는 상황으로 바꿨어요' 안내가 확인된다. 두 번째 변경은 12.721~14.282초에 정상 완료됐다. 자동 복구 실패라고 결론 낼 수 있는 실행이 아니라, 필요한 실패 조건을 설정하지 않은 검사였다. 이 실패를 지우거나 단순 재실행으로 덮지 않는다.

## 검사를 강화한 부분

- 앞선 명령과 후속 화면 갱신이 끝난 뒤에 다음 조건을 선택한다. 임의 sleep이나 서버의 복구 시간을 늘리지 않는다.
- 설정 POST 응답의 HTTP 200, 실제 요청의 `fault`, 서버가 돌려준 `next_transfer_fault`가 모두 원하는 값인지 검사한다. 잘못 설정되면 복구 시험을 진행하지 않는다.
- 변경 POST의 첫 응답 자체가 첫 시나리오에서 REJECTED, 두 번째에서 PENDING인지 저장해 확인한다. PENDING 표시·수동 복구 없이 완료·동일 주문·1회 결제·포인트·6개 비교 결과 단언은 그대로 유지한다.
- 향후 실패 기록에 요청 본문과 마지막 화면 상태도 남긴다. 이 자료는 고정된 가상 주문 정보만 포함하며 인증 정보나 실제 고객 데이터가 아니다.

실제 오류 순서를 흉내 내는 검증 함수 단위 시험 4개를 먼저 실행해 모두 실패한 뒤 수정 후 통과했다. 이 가짜 페이지 단위 시험은 브라우저 실행 증거가 아니다. 실제 검증은 수정된 함수로 최신 PR 및 main에서 다시 실행한다.

이 변경은 검증 스크립트·검증 시험·CI 단계·설명 문서에 한정한다. 제품의 주문·금액·매장 HTTP·복구 동작과 복구 대기 시간은 바꾸지 않는다. 기존 공개 영상은 앱 `000a106…`의 실제 촬영이며 이번 검증 수정이 영상 속 제품 동작을 바꾸지는 않는다.
